## 2. ESP-IDF 配置：最容易"以为改了其实没改"的地方

### 2.1 `sdkconfig` 会覆盖 `sdkconfig.defaults`（坑中之王）

**现象**：改了 `sdkconfig.defaults`，重新编译，行为一点没变。

**根因**：`sdkconfig.defaults` 只在 **`sdkconfig` 不存在时**用来生成它。
一旦 `sdkconfig` 已经存在（第一次编译后就生成了），后续编译**只读 `sdkconfig`**，
你改 `defaults` 等于白改。

**正确做法**：
- 两个文件**一起改**，或者
- 先删掉 `sdkconfig` 再编译（会按 defaults 重新生成），或者
- 用 `idf.py menuconfig` 改（它写的是 `sdkconfig`）。

**自查**：编译完 `grep 你的配置项 sdkconfig`，确认值是你要的。

---

### 2.2 配置项名写错 → 静默忽略，不报错

**现象**：`sdkconfig.defaults` 里写了 `CONFIG_CAMERA_SCCB_USE_I2C=y`，
文档里三处据此宣称"已让 SCCB 走硬件 I2C 共用总线"，看起来一切正常。

**真相**：**这个配置项根本不存在**。esp32-camera 的真实选项名是：

```ini
CONFIG_SCCB_HARDWARE_I2C_DRIVER_NEW=y
CONFIG_SCCB_HARDWARE_I2C_PORT0=y     # 默认是 PORT1，必须显式改
```

Kconfig 遇到不认识的 `CONFIG_XXX` **不报错、不警告，直接扔掉**。
所以这一行完全是空转，文档也跟着一起错了。

**为什么会"看起来正常"**：因为代码里另有一道保险
（`camera.c` 里 `.sccb_i2c_port = I2C_NUM_0`）把它救回来了。
**两道保险同时存在时，你很难发现其中一道是坏的** —— 这是最危险的组合。

**可复用的审计方法**（这次就是靠它查出来的）：

```bash
# 1) 抽出 sdkconfig 里真实存在的所有符号
grep -oE '^#? ?CONFIG_[A-Z0-9_]+' firmware/sdkconfig | sed 's/^#* *//' | sort -u > /tmp/defined.txt
# 2) 抽出全仓文档/代码里引用的所有 CONFIG_XXX
grep -rhoE 'CONFIG_[A-Z0-9_]+' --include='*.md' --include='*.c' --include='*.h' . | sort -u > /tmp/used.txt
# 3) 求差集：用了但不存在 = 空转配置
comm -13 /tmp/defined.txt /tmp/used.txt
```

**建议**：每次改完配置项，都跑一遍这个差集检查。

---

### 2.3 其他必须设对的项（本项目实测）

| 配置项 | 值 | 不设会怎样 |
|---|---|---|
| `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG` | `y` | ESP32-S3-EYE 没有独立 USB 转 UART 芯片，串口监视器**一个字都看不到** |
| `CONFIG_SPIRAM_MODE_OCT` | `y` | 板载是 Octal PSRAM，误选 QUAD 会启动即 `wrong PSRAM line mode` 并 abort |
| `CONFIG_PARTITION_TABLE_CUSTOM` | `y` + `partitions.csv` | 加了 esp32-camera 后体积超 1MB，默认 app 分区装不下 |
| `CONFIG_COMPILER_OPTIMIZATION_PERF` | `y` | `-Og` 会触发 GCC 内部段错误（见 1.1） |

## 3. 硬件与总线

### 3.1 I2C 总线争抢：一个"看起来只是没数据"的坑

**现象**：加上摄像头后，**加速度和摄像头数据一起消失**，一个都不上传。

**根因**：`esp_camera_init()` 默认走软件 SCCB，会在 **I2C 端口 1** 上新建一条总线，
**却仍然用 GPIO4/5** —— 而 QMA7981 用的是**端口 0 的 GPIO4/5**。
两条逻辑总线抢同一对物理线 → 加速度计读失败 → 主循环 `continue` → 全部停传。

**修复**（`camera.c`）：让摄像头**复用**加速度计已经建好的那条总线：

```c
config.pin_sscb_sda = -1;          // -1 = 不新建总线
config.pin_sscb_scl = -1;
config.sccb_i2c_port = I2C_NUM_0;  // 复用端口 0
```

**学到的**：I2C 是**共享总线**，不同地址的设备（0x12 加速度计 / 0x30 摄像头）
本来就能挂在一起。**"新建一条总线"往往是错的，应该"复用"。**

---

### 3.2 芯片 ID 对不上 ≠ 芯片坏了

**现象**：QMA7981 读到的 `CHIP_ID = 0x90`，手册期望 `0xE7`。

**结论**：该寄存器默认值由**芯片 NVM 决定，批次不同可能不一致**。
I2C 通信本身正常（能读到值就说明通信 OK），**不要因此判死硬件**。

固件里的处理：打印警告但继续运行，而不是 abort。

---

### 3.3 用物理约束做现场标定（很实用的技巧）

板子静止时只受重力，**三轴合成加速度 `|a| = √(ax²+ay²+az²)` 恒为 1.000 g，与摆放姿态无关**。

这是**唯一不需要标准器具**就能做的现场标定方法：

```
实测：未标定时 |a| = 0.9116 → 系数取 0.9116
     换姿态后 |a| 只到 0.9266 → 反推未标定值 0.8447 → 修正
     静置 12 条取均值 |a| = 0.9563（标准差 0.0081，确认真的静止）
     → 0.8447 × 0.9563 = 0.8078 → 最终系数
```

**注意**：不同姿态下未标定的 `|a|` 不一样（0.9116 / 0.8447 / 0.8078），
说明该传感器**除灵敏度误差外还有零点偏移**，单一比例系数无法在所有姿态下都得到 1.000。
要彻底解决得上**六面法校准**（本课程不必）。

**用法**：串口打印原始值 + 换算值，网页也显示，**三处对账**。

## 4. 网络：本次最花时间的部分

### 4.1 排查顺序（建议照抄）

**先证明"服务端本身没问题"，再怀疑网络。** 顺序错了会白折腾很久：

```bash
curl http://127.0.0.1:8000/api/health          # 服务端活着吗
curl http://127.0.0.1:8000/api/latest          # 数据接口正常吗
netstat -ano | grep :8000                      # 端口在听吗、有哪些连接
```

**本次的关键判断点**：
> `netstat` 里能看到板子（`10.1.41.106`）到电脑（`10.1.41.151:8000`）的
> **一堆 ESTABLISHED 连接**，但**服务端日志里一条请求都没有**。
>
> 这个组合的含义是：**TCP 握手成功了，但 HTTP 请求数据没送达。**
> 服务端的处理线程卡在"读请求行"上，所以既不报错也不打日志。

这条经验很值钱：**"连接建立了" ≠ "数据到了"**。

---

### 4.2 A-MPDU 聚合被 AP 反复拆除（**重要观察，但实测不是根因**）

**现象**：
```
E esp-tls: [sock=54] select() timeout
E transport_base: Failed to open a new connection: 32774
E HTTP_CLIENT: Connection failed, sock < 0
W HTTP_CLIENT: Connection timed out before data was ready!
```
两种失败交替出现：**连不上**（超时）和**连上了但没响应**。

**关键线索**（串口日志）：
```
I wifi:<ba-add>idx:1 (ifx:0, ...), tid:0, ssn:1, winSize:64
I wifi:<ba-del>idx:1, tid:0                       ← 几百毫秒后立刻被拆
I wifi:<ba-add>idx:1 (ifx:0, ...), tid:0, ssn:3, winSize:64
```
AP 在 **tid:0（数据 TID）** 上**反复「建 Block-ACK 会话 → 立刻拆掉」**。

**当时的推理**：
- **控制帧**（SYN / SYN-ACK / ACK）体积小，走普通 MPDU，**不依赖 BA 会话** → 能过
- **数据帧**（HTTP 请求、响应体）走 **A-MPDU 聚合**，**依赖 BA 会话** → BA 被拆掉就发不出去

所以出现"**TCP 连得上，数据过不去**"的怪现象。

**实验**：关掉聚合，数据帧改单帧发送
```ini
CONFIG_ESP_WIFI_AMPDU_TX_ENABLED=n
CONFIG_ESP_WIFI_AMPDU_RX_ENABLED=n
```
（已验证设置确实生效：编译后 `sdkconfig` 里是 `is not set`，IDF 没有偷偷改回来。）

**结果：❌ 无效**。关闭后上传依旧大面积失败（50 秒内 0 成功）。
**结论：根因不在聚合层，已回退到 IDF 默认值。**

> 这个"无效实验"本身也值得记下来 —— 免得以后重复做一遍。
> 同时它说明一件事：**串口日志里的异常现象（BA 反复重协商）可能是"结果"而不是"原因"**，
> 链路本身不稳时，AP 就会不断拆 BA。看到异常日志别急着当成根因。

### 4.3 Wi-Fi 省电模式（另一个常见坑）

**现象**：Wi-Fi 显示已连接、**RSSI 高达 -36 dBm**（信号极好），但 HTTP 一直连不上。

**根因**：ESP-IDF 默认让 STA 进入 `WIFI_PS_MIN_MODEM`（省电最小模式），
串口能看到 `wifi:pm start, type: 1`。板子按「监听间隔」周期休眠，
**入站帧由 AP 缓存，等到 DTIM 才下发**；某些 AP 还会把监听间隔放大：

```
I wifi:dp: 1, bi: 102400, li: 3, scale listen interval from 307200 us to 307200 us
                                          ↑ 102ms 被放大到 307ms
```

板子发完 SYN 就睡，SYN-ACK 被 AP 压着不发 → `select() timeout`。

**修复**（`main.c`，必须在 `esp_wifi_start()` 之后）：

```c
ESP_ERROR_CHECK(esp_wifi_set_ps(WIFI_PS_NONE));
```

修复后日志变成 `wifi:Set ps type: 0` / `wifi:pm start, type: 0`。

**判断技巧**：`type: 1` = 省电开着，`type: 0` = 已关闭。

> 注：本次实测关掉省电后问题依旧，所以省电**不是**本项目的根因，
> 但它确实是同类症状的常见原因，**排查时应该顺手关掉排除掉**。

### 4.4 Windows 防火墙：网络位置是"公用"时默认拦入站

**现象**：板子连不上，但服务端一切正常。

**排查**：
```powershell
Get-NetFirewallProfile | Select Name,Enabled,DefaultInboundAction
Get-NetConnectionProfile | Select Name,NetworkCategory     # ← 关键
```
本次结果：网络位置 = **Public（公用）**，策略 = **BlockInbound, AllowOutbound**。

**注意**：Windows 防火墙的放行规则是**按程序完整路径**记的。
你换了个 Python（比如从系统 Python 换成托管版 3.13.12），
**新路径没有放行规则，入站就被拦**。

**查规则**（按程序名筛，避免遍历几百条规则卡死）：
```powershell
Get-NetFirewallRule -Direction Inbound |
  Where-Object { $_.DisplayName -like '*python*' } |
  Select-Object DisplayName,Action,Enabled,Profile
# 再看它绑的是哪个程序路径
Get-NetFirewallRule -Direction Inbound |
  Where-Object { $_.DisplayName -like '*python*' } |
  Get-NetFirewallApplicationFilter | Select Program
```

**放行**（需要管理员）：
```powershell
New-NetFirewallRule -DisplayName "AI-interaction 8000" `
  -Direction Inbound -LocalPort 8000 -Protocol TCP -Action Allow -Profile Any
```

**本次结论**：规则里已经有当前 Python 路径的 TCP/UDP 全端口 Allow，
**所以防火墙不是本次的根因** —— 但排查时必须先排除它。

### 4.5 校园网的两个坑

1. **AP 隔离**：校园网/公司网若开了客户端隔离，设备之间无法互访，任务直接失败。
2. **频段/网段陷阱**（本项目实测记录）：
   - **"431"** = 2.4G 主网 → `10.1.41.x`，**与电脑同网段，可用**
   - **"432"** = 5G/IoT → `10.1.42.x`，**被隔离，回包不通，不要连**
   - ESP32-S3 **不支持 5GHz**，这本身就是最常见的失败原因之一。

**判断技巧**：板子能不能通，看两件事——
- 能不能 **SNTP 对时**（`ntp.aliyun.com`）。**对时失败 = 板子出不了外网。**
- 电脑 `ping 板子IP` 通不通。

本次现象：**DHCP 拿到 IP、ARP 正常、RSSI -36，但 SNTP 失败、ping 不通、HTTP 约 98% 失败** ——
典型的"局域网内被策略限制"，不是板子坏了。

---

### 4.6 诚实地处理"没拿到时间"

SNTP 失败时**绝不伪造日期**，而是明确标注：

```
ts_device: "uptime+12.660s(time_not_synced)"
```

**这是好习惯**：数据可以不全，但不能假。
老师检查时一眼就能看出"这条数据的时间没同步"，比编一个看起来正常的假时间戳诚实得多。

### 5.3 沙箱里 `git push` 挂死 ≠ 网络问题

**现象**：`git push` 打印 `Pushing to ...` 后**无任何输出，直到超时**。

**诊断步骤**（很重要，别急着怀疑网络）：
```bash
# 1) 先测网络/代理是否通
curl --proxy http://127.0.0.1:7897 -sI \
  "https://github.com/<user>/<repo>.git/info/refs?service=git-upload-pack" | head -1
# 返回 200 → 网络没问题

# 2) 再禁用凭据助手，看它报什么
git -c credential.helper= push
# 立刻报 "could not read Username ... terminal prompts disabled"
# → 是【凭据】问题，不是网络问题
```

**绕过办法**：取出令牌，临时放进 URL（用完立刻换掉，不留痕）
```bash
TOKEN=$(printf 'protocol=https\nhost=github.com\n\n' | git credential fill | sed -n 's/^password=//p')
GIT_TERMINAL_PROMPT=0 git -c credential.helper= push \
  "https://<user>:${TOKEN}@github.com/<user>/<repo>.git" main
```

### 5.4 进阶：`credential.helper` 被包了一层，导致取不到凭据

**现象**：`git credential fill` **不报错、返回空**（rc=0，没有任何输出），
于是上面那条 `TOKEN=...` 取到空字符串，推送直接失败。

**根因**：本机 `git config credential.helper` 的值不是 GCM 本身，而是一个中间层：

```
$ git config --get-all credential.helper
helper-selector
!"C:/Users/.../PortableGit/.../mingw64/bin/git-credential-manager.exe"
```

`helper-selector` 会去查 `credential.helperselector.selected`，
**这一步没选出来，整个链路就静默返回空** —— 不报错，最难查。

**诊断**：用 `GIT_TRACE=1` 看它到底调了什么：
```bash
printf 'protocol=https\nhost=github.com\n\n' | GIT_TRACE=1 git credential fill
# 会看到它执行 'git credential-helper-selector get'，然后就没有下文了
```

**解决**：**绕开中间层，直接调 GCM 二进制**
```bash
GCM="C:/Users/user/.workbuddy-ai/binaries/PortableGit/versions/1.2.0/mingw64/bin/git-credential-manager.exe"
TOKEN=$(printf 'protocol=https\nhost=github.com\n\n' \
  | GCM_INTERACTIVE=never "$GCM" get | sed -n 's/^password=//p')
```
这样就能正常拿到 `username=hongls68` + 40 字符的 OAuth 令牌。

**顺带确认凭据还在不在**（凭据管理器里）：
```powershell
cmdkey /list | Select-String 'github'
# 目标: LegacyGeneric:target=git:https://github.com   用户: hongls68
```

> **教训**：命令"成功返回但结果是空的"，比"报错"难查得多。
> 遇到这种，第一反应应该是 **加 trace / 逐层拆开看每一步的实际输出**，
> 而不是怀疑自己的用法。

### 5.5 仓库公开 + 凭据入库 = 事故

`app_config.h` 里含 Wi-Fi 名称和密码，而仓库是 **public**。

**正确做法**：
- 凭据放进**不进版本库**的 `secrets.h`，并在 `.gitignore` 中忽略它
- `app_config.h` 里用 `#include "secrets.h"`，并提供 `secrets.h.example` 模板
- 提交前用 `git log --all --full-history -- '*secret*'` 之类的方式自查

`ensurepip` 报 `OSError: SHFileOperationW 失败: 0x2`。

**根因**：沙箱通过环境变量注入了一个 `sitecustomize.py`，
把 `os.unlink` 重定向成"移到回收站"。回收站在某些情况下失败，于是整个删除操作崩掉。

**绕过**：**清空 `PYTHONPATH`** 再跑 Python：
```bash
PYTHONPATH="" python -m pip install ...
```

### 6.2 `onnxsim` × `protobuf` 的 ABI 冲突

**现象**：`import onnxsim` **静默崩溃**（SIGTERM，没有任何输出）。

**根因**：`onnxsim 0.4.36` 的 C++ 扩展与 `protobuf 7.x` **ABI 不兼容**。

**修复**：把 protobuf 降到 5.x
```bash
pip install "protobuf==5.29.5"
```

> 这类"import 就静默死掉、没有任何报错"的问题，**九成是 C 扩展 ABI 不匹配**，
> 优先怀疑依赖版本，而不是自己的代码。

### 6.3 ESP-IDF 在受限 shell 里不编译

沙箱里缺 `MSYSTEM`、`PROCESSOR_ARCHITECTURE`，且 `IDF_TOOLS_PATH` 指向了错误位置，
直接跑 `idf.py` **只会打印 MSys 警告然后什么都不做**。

**解决**：写一个启动器（`.idf_launch.py`，已 gitignore）：
剔除 `MSYSTEM`、设 `IDF_TOOLS_PATH`、补 `PROCESSOR_ARCHITECTURE`、
把工具链 bin 注入 `PATH`，再调 `idf.py`。

## 7. 可复用的排查方法论（最值得学的部分）

### 7.1 三处对账

同一份数据在**三个地方**都能看到，互相印证：
1. **板端串口**：`raw: x=-411 y=-282 z=-1157 | g: ax=-0.497 ay=-0.341 az=-1.399`
2. **服务端数据库**：`ax_raw=-421 ay_raw=-280 az_raw=-1161`
3. **网页显示**

任何一处对不上，问题就定位到那一段链路。**这比猜快得多。**

### 7.2 二分法排除

一次只改一个变量，用 A/B 对照：

| 假设 | 实验 | 结果 |
|---|---|---|
| 是防火墙？ | 查规则 + 用 curl 自测 | ❌ 规则已放行，排除 |
| 是服务端？ | `curl /api/health` | ❌ 200 OK，排除 |
| 是省电模式？ | `esp_wifi_set_ps(WIFI_PS_NONE)` | ❌ 关掉仍失败，排除 |
| 是摄像头占带宽？ | `CAMERA_ENABLE=0` 重烧 | ❌ 45 秒 74 次全失败，排除 |
| 是 A-MPDU 聚合？ | `CONFIG_ESP_WIFI_AMPDU_*_ENABLED=n` 重烧 | ❌ 50 秒 0 成功，排除 |
| 是校园网链路？ | 已无固件侧假设可排除 | ⚠️ **剩余嫌疑** |

**关键**：每个假设都要**做实验**，不能靠"我觉得"。
本次前五个假设全是错的，正是靠实验一个个排除，才把范围收窄到"网络链路本身"。

### 7.3 从"证据矛盾"入手

本次最有价值的一步，是发现了一个**矛盾**：

> 服务端 `netstat` 显示有 ESTABLISHED 连接，
> 但服务端日志里**一条请求都没有**。

**矛盾点就是突破口。** 顺着它推出"**控制帧能过、数据帧过不去**"这个关键判断，
一下子把怀疑范围从"整个网络"收窄到"数据帧传输"这一层，
后续的省电、聚合、摄像头三个实验都是围绕这个判断设计的。

（虽然最后证明聚合不是根因，但如果没有这个判断，就只能在"网络不通"这种模糊描述里打转。）

### 7.4 先看板子自己怎么说

串口日志里的每一行都有价值。本次的关键线索全在启动日志里：
- `wifi:pm start, type: 1` → 省电开着
- `ba-add` / `ba-del` 循环 → 聚合异常
- `scale listen interval ... 307200 us` → AP 放大了监听间隔
- `SNTP 对时失败` → 板子出不了外网

**养成习惯：出问题先完整抓一次启动日志，别只看报错那几行。**

## 8. 代码层面两个小改进（本次做的）

1. **不要吞掉错误码**（`main.c` 的 `upload_frame`）
   ```c
   // 改前：把真实原因统一压成 ESP_FAIL，串口只剩「帧上传失败: ESP_FAIL」
   if (esp_http_client_open(client, len) == ESP_OK) { ... } else { err = ESP_FAIL; }
   // 改后：原样保留 ESP_ERR_HTTP_CONNECT / ESP_ERR_HTTP_READ_TIMEOUT 等
   esp_err_t err = esp_http_client_open(client, len);
   ```
   **真实错误码是排查问题的唯一线索，压掉它等于自断线索。**

2. **单次 POST 超时从 5s 放宽到 8s**（`UPLOAD_TIMEOUT_MS`）
   链路丢包时，20~25KB 的整帧 POST 容易在"连上了但还没回"时被误判失败。

**还没完全解决的：链路间歇性**
- 观察到的模式：**板子刚重启后有一段约 50 秒的良好窗口**（能稳定 1 条/秒上传），
  之后退化到几乎全失败，过一段时间又恢复一小段。
- 已排除：防火墙、服务端、Wi-Fi 省电、摄像头带宽、A-MPDU 聚合（见 7.2 表格）。
- 剩余嫌疑：**校园网 AP 链路/策略本身**。
  佐证：板子 **SNTP 对时失败**（出不了外网）、电脑 **ping 板子不通**、
  但 **RSSI 高达 -36 dBm**、DHCP/ARP 正常。
  典型的"局域网内被策略限制"或"AP 对该客户端不稳定"，不是板子坏了。

**建议的下一步（按推荐顺序）：**
1. **换个网络试**：用手机热点（或随身路由器），让**电脑和板子连同一个热点**。
   这一步能一次性排除校园网。注意本项目电脑**没有 Wi-Fi 网卡**（只有有线），
   所以要用 **手机 USB 网络共享**，或给电脑加个 USB 无线网卡。
2. **换 AP / 换位置**：同一个 SSID 可能有多个 AP，换个位置可能连到另一个。
3. **降低单帧体积**：摄像头分辨率从 800x600 降到 VGA(640x480)，减少链路压力。

## 11. 可以去学的（按性价比排序）

1. **ESP-IDF 的 Kconfig 机制**：`sdkconfig` / `sdkconfig.defaults` / `menuconfig` 三者关系。
   —— 理解了就不会再踩 2.1、2.2。
