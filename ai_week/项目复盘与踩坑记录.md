## 2. ESP-IDF 配置：最容易"以为改了其实没改"的地方

### 2.1 `sdkconfig` 会覆盖 `sdkconfig.defaults`（坑中之王）

**现象**：改了 `sdkconfig.defaults`，重新编译，行为一点没变。

**根因**：`sdkconfig.defaults` 只在 **`sdkconfig` 不存在时**用来生成它。
一旦 `sdkconfig` 已经存在（第一次编译后就生成了），后续编译**只读 `sdkconfig`**，
你改 `defaults` 等于白改。

**正确做法**：
- 两个文件**一起改**，或者
- 先删掉 `sdkconfig` 再编译（会按 defaults 重新生成），或者
- 用 `idf.py menuconfig` 改（它写的是 `sdkconfig`）。

**自查**：编译完 `grep 你的配置项 sdkconfig`，确认值是你要的。

---

### 2.2 配置项名写错 → 静默忽略，不报错

**现象**：`sdkconfig.defaults` 里写了 `CONFIG_CAMERA_SCCB_USE_I2C=y`，
文档里三处据此宣称"已让 SCCB 走硬件 I2C 共用总线"，看起来一切正常。

**真相**：**这个配置项根本不存在**。esp32-camera 的真实选项名是：

```ini
CONFIG_SCCB_HARDWARE_I2C_DRIVER_NEW=y
CONFIG_SCCB_HARDWARE_I2C_PORT0=y     # 默认是 PORT1，必须显式改
```

Kconfig 遇到不认识的 `CONFIG_XXX` **不报错、不警告，直接扔掉**。
所以这一行完全是空转，文档也跟着一起错了。

**为什么会"看起来正常"**：因为代码里另有一道保险
（`camera.c` 里 `.sccb_i2c_port = I2C_NUM_0`）把它救回来了。
**两道保险同时存在时，你很难发现其中一道是坏的** —— 这是最危险的组合。

**可复用的审计方法**（这次就是靠它查出来的）：

```bash
# 1) 抽出 sdkconfig 里真实存在的所有符号
grep -oE '^#? ?CONFIG_[A-Z0-9_]+' firmware/sdkconfig | sed 's/^#* *//' | sort -u > /tmp/defined.txt
# 2) 抽出全仓文档/代码里引用的所有 CONFIG_XXX
grep -rhoE 'CONFIG_[A-Z0-9_]+' --include='*.md' --include='*.c' --include='*.h' . | sort -u > /tmp/used.txt
# 3) 求差集：用了但不存在 = 空转配置
comm -13 /tmp/defined.txt /tmp/used.txt
```

**建议**：每次改完配置项，都跑一遍这个差集检查。

---

### 2.3 其他必须设对的项（本项目实测）

| 配置项 | 值 | 不设会怎样 |
|---|---|---|
| `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG` | `y` | ESP32-S3-EYE 没有独立 USB 转 UART 芯片，串口监视器**一个字都看不到** |
| `CONFIG_SPIRAM_MODE_OCT` | `y` | 板载是 Octal PSRAM，误选 QUAD 会启动即 `wrong PSRAM line mode` 并 abort |
| `CONFIG_PARTITION_TABLE_CUSTOM` | `y` + `partitions.csv` | 加了 esp32-camera 后体积超 1MB，默认 app 分区装不下 |
| `CONFIG_COMPILER_OPTIMIZATION_PERF` | `y` | `-Og` 会触发 GCC 内部段错误（见 1.1） |

## 3. 硬件与总线

### 3.1 I2C 总线争抢：一个"看起来只是没数据"的坑

**现象**：加上摄像头后，**加速度和摄像头数据一起消失**，一个都不上传。

**根因**：`esp_camera_init()` 默认走软件 SCCB，会在 **I2C 端口 1** 上新建一条总线，
**却仍然用 GPIO4/5** —— 而 QMA7981 用的是**端口 0 的 GPIO4/5**。
两条逻辑总线抢同一对物理线 → 加速度计读失败 → 主循环 `continue` → 全部停传。

**修复**（`camera.c`）：让摄像头**复用**加速度计已经建好的那条总线：

```c
config.pin_sscb_sda = -1;          // -1 = 不新建总线
config.pin_sscb_scl = -1;
config.sccb_i2c_port = I2C_NUM_0;  // 复用端口 0
```

**学到的**：I2C 是**共享总线**，不同地址的设备（0x12 加速度计 / 0x30 摄像头）
本来就能挂在一起。**"新建一条总线"往往是错的，应该"复用"。**

---

### 3.2 芯片 ID 对不上 ≠ 芯片坏了

**现象**：QMA7981 读到的 `CHIP_ID = 0x90`，手册期望 `0xE7`。

**结论**：该寄存器默认值由**芯片 NVM 决定，批次不同可能不一致**。
I2C 通信本身正常（能读到值就说明通信 OK），**不要因此判死硬件**。

固件里的处理：打印警告但继续运行，而不是 abort。

---

### 3.3 用物理约束做现场标定（很实用的技巧）

板子静止时只受重力，**三轴合成加速度 `|a| = √(ax²+ay²+az²)` 恒为 1.000 g，与摆放姿态无关**。

这是**唯一不需要标准器具**就能做的现场标定方法：

```
实测：未标定时 |a| = 0.9116 → 系数取 0.9116
     换姿态后 |a| 只到 0.9266 → 反推未标定值 0.8447 → 修正
     静置 12 条取均值 |a| = 0.9563（标准差 0.0081，确认真的静止）
     → 0.8447 × 0.9563 = 0.8078 → 最终系数
```

**注意**：不同姿态下未标定的 `|a|` 不一样（0.9116 / 0.8447 / 0.8078），
说明该传感器**除灵敏度误差外还有零点偏移**，单一比例系数无法在所有姿态下都得到 1.000。
要彻底解决得上**六面法校准**（本课程不必）。

**用法**：串口打印原始值 + 换算值，网页也显示，**三处对账**。

## 4. 网络：本次最花时间的部分

### 4.1 排查顺序（建议照抄）

**先证明"服务端本身没问题"，再怀疑网络。** 顺序错了会白折腾很久：

```bash
curl http://127.0.0.1:8000/api/health          # 服务端活着吗
curl http://127.0.0.1:8000/api/latest          # 数据接口正常吗
netstat -ano | grep :8000                      # 端口在听吗、有哪些连接
```

**本次的关键判断点**：
> `netstat` 里能看到板子（`10.1.41.106`）到电脑（`10.1.41.151:8000`）的
> **一堆 ESTABLISHED 连接**，但**服务端日志里一条请求都没有**。
>
> 这个组合的含义是：**TCP 握手成功了，但 HTTP 请求数据没送达。**
> 服务端的处理线程卡在"读请求行"上，所以既不报错也不打日志。

这条经验很值钱：**"连接建立了" ≠ "数据到了"**。

---

### 4.2 A-MPDU 聚合被 AP 反复拆除（**重要观察，但实测不是根因**）

**现象**：
```
E esp-tls: [sock=54] select() timeout
E transport_base: Failed to open a new connection: 32774
E HTTP_CLIENT: Connection failed, sock < 0
W HTTP_CLIENT: Connection timed out before data was ready!
```
两种失败交替出现：**连不上**（超时）和**连上了但没响应**。

**关键线索**（串口日志）：
```
I wifi:<ba-add>idx:1 (ifx:0, ...), tid:0, ssn:1, winSize:64
I wifi:<ba-del>idx:1, tid:0                       ← 几百毫秒后立刻被拆
I wifi:<ba-add>idx:1 (ifx:0, ...), tid:0, ssn:3, winSize:64
```
AP 在 **tid:0（数据 TID）** 上**反复「建 Block-ACK 会话 → 立刻拆掉」**。

**当时的推理**：
- **控制帧**（SYN / SYN-ACK / ACK）体积小，走普通 MPDU，**不依赖 BA 会话** → 能过
- **数据帧**（HTTP 请求、响应体）走 **A-MPDU 聚合**，**依赖 BA 会话** → BA 被拆掉就发不出去

所以出现"**TCP 连得上，数据过不去**"的怪现象。

**实验**：关掉聚合，数据帧改单帧发送
```ini
CONFIG_ESP_WIFI_AMPDU_TX_ENABLED=n
CONFIG_ESP_WIFI_AMPDU_RX_ENABLED=n
```
（已验证设置确实生效：编译后 `sdkconfig` 里是 `is not set`，IDF 没有偷偷改回来。）

**结果：❌ 无效**。关闭后上传依旧大面积失败（50 秒内 0 成功）。
**结论：根因不在聚合层，已回退到 IDF 默认值。**

> 这个"无效实验"本身也值得记下来 —— 免得以后重复做一遍。
> 同时它说明一件事：**串口日志里的异常现象（BA 反复重协商）可能是"结果"而不是"原因"**，
> 链路本身不稳时，AP 就会不断拆 BA。看到异常日志别急着当成根因。

### 4.3 Wi-Fi 省电模式（另一个常见坑）

**现象**：Wi-Fi 显示已连接、**RSSI 高达 -36 dBm**（信号极好），但 HTTP 一直连不上。

**根因**：ESP-IDF 默认让 STA 进入 `WIFI_PS_MIN_MODEM`（省电最小模式），
串口能看到 `wifi:pm start, type: 1`。板子按「监听间隔」周期休眠，
**入站帧由 AP 缓存，等到 DTIM 才下发**；某些 AP 还会把监听间隔放大：

```
I wifi:dp: 1, bi: 102400, li: 3, scale listen interval from 307200 us to 307200 us
                                          ↑ 102ms 被放大到 307ms
```

板子发完 SYN 就睡，SYN-ACK 被 AP 压着不发 → `select() timeout`。

**修复**（`main.c`，必须在 `esp_wifi_start()` 之后）：

```c
ESP_ERROR_CHECK(esp_wifi_set_ps(WIFI_PS_NONE));
```

修复后日志变成 `wifi:Set ps type: 0` / `wifi:pm start, type: 0`。

**判断技巧**：`type: 1` = 省电开着，`type: 0` = 已关闭。

> 注：本次实测关掉省电后问题依旧，所以省电**不是**本项目的根因，
> 但它确实是同类症状的常见原因，**排查时应该顺手关掉排除掉**。

### 4.4 Windows 防火墙：网络位置是"公用"时默认拦入站

**现象**：板子连不上，但服务端一切正常。

**排查**：
```powershell
Get-NetFirewallProfile | Select Name,Enabled,DefaultInboundAction
Get-NetConnectionProfile | Select Name,NetworkCategory     # ← 关键
```
本次结果：网络位置 = **Public（公用）**，策略 = **BlockInbound, AllowOutbound**。

**注意**：Windows 防火墙的放行规则是**按程序完整路径**记的。
你换了个 Python（比如从系统 Python 换成托管版 3.13.12），
**新路径没有放行规则，入站就被拦**。

**查规则**（按程序名筛，避免遍历几百条规则卡死）：
```powershell
Get-NetFirewallRule -Direction Inbound |
  Where-Object { $_.DisplayName -like '*python*' } |
  Select-Object DisplayName,Action,Enabled,Profile
# 再看它绑的是哪个程序路径
Get-NetFirewallRule -Direction Inbound |
  Where-Object { $_.DisplayName -like '*python*' } |
  Get-NetFirewallApplicationFilter | Select Program
```

**放行**（需要管理员）：
```powershell
New-NetFirewallRule -DisplayName "AI-interaction 8000" `
  -Direction Inbound -LocalPort 8000 -Protocol TCP -Action Allow -Profile Any
```

**本次结论**：规则里已经有当前 Python 路径的 TCP/UDP 全端口 Allow，
**所以防火墙不是本次的根因** —— 但排查时必须先排除它。

### 4.5 校园网的两个坑

1. **AP 隔离**：校园网/公司网若开了客户端隔离，设备之间无法互访，任务直接失败。
2. **频段/网段陷阱**（本项目实测记录）：
   - **"431"** = 2.4G 主网 → `10.1.41.x`，**与电脑同网段，可用**
   - **"432"** = 5G/IoT → `10.1.42.x`，**被隔离，回包不通，不要连**
   - ESP32-S3 **不支持 5GHz**，这本身就是最常见的失败原因之一。

**判断技巧**：板子能不能通，看两件事——
- 能不能 **SNTP 对时**（`ntp.aliyun.com`）。**对时失败 = 板子出不了外网。**
- 电脑 `ping 板子IP` 通不通。

本次现象：**DHCP 拿到 IP、ARP 正常、RSSI -36，但 SNTP 失败、ping 不通、HTTP 约 98% 失败** ——
典型的"局域网内被策略限制"，不是板子坏了。

---

### 4.6 诚实地处理"没拿到时间"

SNTP 失败时**绝不伪造日期**，而是明确标注：

```
ts_device: "uptime+12.660s(time_not_synced)"
```

**这是好习惯**：数据可以不全，但不能假。
老师检查时一眼就能看出"这条数据的时间没同步"，比编一个看起来正常的假时间戳诚实得多。

### 5.3 沙箱里 `git push` 挂死 ≠ 网络问题

**现象**：`git push` 打印 `Pushing to ...` 后**无任何输出，直到超时**。

**诊断步骤**（很重要，别急着怀疑网络）：
```bash
# 1) 先测网络/代理是否通
curl --proxy http://127.0.0.1:7897 -sI \
  "https://github.com/<user>/<repo>.git/info/refs?service=git-upload-pack" | head -1
# 返回 200 → 网络没问题

# 2) 再禁用凭据助手，看它报什么
git -c credential.helper= push
# 立刻报 "could not read Username ... terminal prompts disabled"
# → 是【凭据】问题，不是网络问题
```

**绕过办法**：取出令牌，临时放进 URL（用完立刻换掉，不留痕）
```bash
TOKEN=$(printf 'protocol=https\nhost=github.com\n\n' | git credential fill | sed -n 's/^password=//p')
GIT_TERMINAL_PROMPT=0 git -c credential.helper= push \
  "https://<user>:${TOKEN}@github.com/<user>/<repo>.git" main
```

### 5.4 进阶：`credential.helper` 被包了一层，导致取不到凭据

**现象**：`git credential fill` **不报错、返回空**（rc=0，没有任何输出），
于是上面那条 `TOKEN=...` 取到空字符串，推送直接失败。

**根因**：本机 `git config credential.helper` 的值不是 GCM 本身，而是一个中间层：

```
$ git config --get-all credential.helper
helper-selector
!"C:/Users/.../PortableGit/.../mingw64/bin/git-credential-manager.exe"
```

`helper-selector` 会去查 `credential.helperselector.selected`，
**这一步没选出来，整个链路就静默返回空** —— 不报错，最难查。

**诊断**：用 `GIT_TRACE=1` 看它到底调了什么：
```bash
printf 'protocol=https\nhost=github.com\n\n' | GIT_TRACE=1 git credential fill
# 会看到它执行 'git credential-helper-selector get'，然后就没有下文了
```

**解决**：**绕开中间层，直接调 GCM 二进制**
```bash
GCM="C:/Users/user/.workbuddy-ai/binaries/PortableGit/versions/1.2.0/mingw64/bin/git-credential-manager.exe"
TOKEN=$(printf 'protocol=https\nhost=github.com\n\n' \
  | GCM_INTERACTIVE=never "$GCM" get | sed -n 's/^password=//p')
```
这样就能正常拿到 `username=hongls68` + 40 字符的 OAuth 令牌。

**顺带确认凭据还在不在**（凭据管理器里）：
```powershell
cmdkey /list | Select-String 'github'
# 目标: LegacyGeneric:target=git:https://github.com   用户: hongls68
```

> **教训**：命令"成功返回但结果是空的"，比"报错"难查得多。
> 遇到这种，第一反应应该是 **加 trace / 逐层拆开看每一步的实际输出**，
> 而不是怀疑自己的用法。

### 5.4.1 补记（2026-09-21）：根因找到了，以及一条能直接用的推送命令

**根因**：`helper-selector` 之所以"卡住 / 静默返回空"，是因为它内部执行了

```
git config --system -e        ← 注意这个 -e
```

`-e` 是 **edit**，会去打开系统级 `gitconfig` 的**编辑器**。在非交互 shell 里没人能编辑，
于是它就**挂在那里等编辑器退出**。用 `GIT_TRACE=1` 能看到这段空档：

```
15:24:54.862  git config --system -e          ← 开始
15:25:28.565  git-credential-manager.exe get  ← 34 秒后才走到下一步
```

整整 34 秒白白耗掉。所以现象是「推送挂死」，**但凭据本身是好的** ——
只要绕过中间层，GCM 立刻就能返回 `username=hongls68` 和令牌。

**可用的推送命令**（`credential.helper=` 空值用来清空已有助手列表，再只挂 GCM）：

```bash
GCM="C:/Users/user/.workbuddy-ai/binaries/PortableGit/versions/1.2.0/mingw64/bin/git-credential-manager.exe"

GCM_INTERACTIVE=never GIT_TERMINAL_PROMPT=0 \
  git -c credential.helper= -c "credential.helper=!$GCM" push origin main
```

实测输出：

```
To https://github.com/hongls68/zuoye.git
   bee01d4..a1dc9bf  main -> main
```

**排查顺序（照抄即可）**：

```bash
# 1) 先确认网络没问题（这一步能通，就说明代理和 DNS 都是好的）
git ls-remote origin

# 2) 再单独问 GCM 要凭据（能返回 username/password 就说明凭据没问题）
printf 'protocol=https\nhost=github.com\n\n' | GCM_INTERACTIVE=never "$GCM" get

# 3) 两者都通还推不上去 → 一定是中间层，加 GIT_TRACE=1 找那 30 多秒的空档
```

> **教训（比 5.4 更值钱的一条）**：**"卡住"和"没凭据"是两回事。**
> 这次真正的坑不是认证失败，而是一个**会打开编辑器的配置命令被塞进了自动化链路**。
> 以后凡是在非交互环境里调用别人的工具链，都要问一句：
> **它会不会在某个分支上去要一个 stdin / 编辑器 / GUI？**

### 5.5 仓库公开 + 凭据入库 = 事故

`app_config.h` 里含 Wi-Fi 名称和密码，而仓库是 **public**。

**正确做法**：
- 凭据放进**不进版本库**的 `secrets.h`，并在 `.gitignore` 中忽略它
- `app_config.h` 里用 `#include "secrets.h"`，并提供 `secrets.h.example` 模板
- 提交前用 `git log --all --full-history -- '*secret*'` 之类的方式自查

## 7. 可复用的排查方法论（最值得学的部分）

### 7.1 三处对账

同一份数据在**三个地方**都能看到，互相印证：
1. **板端串口**：`raw: x=-411 y=-282 z=-1157 | g: ax=-0.497 ay=-0.341 az=-1.399`
2. **服务端数据库**：`ax_raw=-421 ay_raw=-280 az_raw=-1161`
3. **网页显示**

任何一处对不上，问题就定位到那一段链路。**这比猜快得多。**

### 7.2 二分法排除

一次只改一个变量，用 A/B 对照：

| 假设 | 实验 | 结果 |
|---|---|---|
| 是防火墙？ | 查规则 + 用 curl 自测 | ❌ 规则已放行，排除 |
| 是服务端？ | `curl /api/health` | ❌ 200 OK，排除 |
| 是省电模式？ | `esp_wifi_set_ps(WIFI_PS_NONE)` | ❌ 关掉仍失败，排除 |
| 是摄像头占带宽？ | `CAMERA_ENABLE=0` 重烧 | ❌ 45 秒 74 次全失败，排除 |
| 是 A-MPDU 聚合？ | `CONFIG_ESP_WIFI_AMPDU_*_ENABLED=n` 重烧 | ❌ 50 秒 0 成功，排除 |
| 是校园网链路？ | 已无固件侧假设可排除 | ⚠️ **剩余嫌疑** |

**关键**：每个假设都要**做实验**，不能靠"我觉得"。
本次前五个假设全是错的，正是靠实验一个个排除，才把范围收窄到"网络链路本身"。

### 7.3 从"证据矛盾"入手

本次最有价值的一步，是发现了一个**矛盾**：

> 服务端 `netstat` 显示有 ESTABLISHED 连接，
> 但服务端日志里**一条请求都没有**。

**矛盾点就是突破口。** 顺着它推出"**控制帧能过、数据帧过不去**"这个关键判断，
一下子把怀疑范围从"整个网络"收窄到"数据帧传输"这一层，
后续的省电、聚合、摄像头三个实验都是围绕这个判断设计的。

（虽然最后证明聚合不是根因，但如果没有这个判断，就只能在"网络不通"这种模糊描述里打转。）

### 7.4 先看板子自己怎么说

串口日志里的每一行都有价值。本次的关键线索全在启动日志里：
- `wifi:pm start, type: 1` → 省电开着
- `ba-add` / `ba-del` 循环 → 聚合异常
- `scale listen interval ... 307200 us` → AP 放大了监听间隔
- `SNTP 对时失败` → 板子出不了外网

**养成习惯：出问题先完整抓一次启动日志，别只看报错那几行。**

## 6. 服务端与模型层的坑（第 3、4 周）

### 6.1 新表没有 `id` 列，却照抄了 `ORDER BY id DESC` → 服务端启动即崩

`commands` 表有自增 `id`，所以写查询时肌肉记忆就是 `ORDER BY id DESC`。
新加的 `help_events` 用 `event_id`(TEXT) 做主键，**根本没有 `id` 列**，
于是 `init_db()` 里建索引那一句直接抛：

```
sqlite3.OperationalError: no such column: id
```

服务端**连启动都启动不了**。更隐蔽的是：同一个错误在查询接口里也有一份，
只在真的调用列表接口时才炸。

**教训**：新表的第一件事是确认**主键形态**，再决定排序字段。
排序字段应该跟着"业务上的新旧"走（`received_at`），而不是跟着"有没有 id"走。

### 6.2 接口里抛异常，客户端只看到"连接被断开"，服务端一行日志都没有

同一个 `ORDER BY id` 出现在 `_handle_help_list` 里，运行时抛异常后 HTTP 层**直接断连接**：

```
http.client.RemoteDisconnected: Remote end closed connection without response
```

而服务端这边**什么都没有** —— 不打印、不记录、返回码都没有。只能靠猜。

**修复**：在分发层加统一兜底 —— `do_GET` / `do_POST` 外层 try/except，
打印完整 traceback 并回 500 JSON；`BrokenPipeError` / `ConnectionResetError` 单独放过
（客户端自己走了不算错误）。

```python
def do_GET(self):
    try:
        self._route_get()
    except (BrokenPipeError, ConnectionResetError):
        pass
    except Exception:
        self._handle_unexpected("GET")
```

**为什么这次一定要补**：这和第 2 周 `_send_json` 漏写响应体那次是**同一类问题** ——
错误发生在**响应写出之后或之外**时，服务端日志会显示"200、一切正常"，
而客户端什么都拿不到。这类 bug 靠看日志永远发现不了，只能靠**端到端自测**。

### 6.3 ★ 出口守卫的误伤：子串匹配把"复述用户的疑问"当成"假成功"

第 4 周要给模型加一道"不许说已采集成功"的守卫。第一版很朴素：文案里出现
`已采集成功 / 拍好了 / 采集完成` 等词、且没有 `COMPLETED` 证据 → 拦下。

实测立刻翻车：用户问 **"让板子拍一张，然后告诉我拍好了没"**，
模型老老实实反问 ——

> "要我对 s3eye-group01 发起一次新采集吗？确认后我就下发指令，
> 再用 get_command_status 查结果**告诉你拍好了没**。"

这句话里出现了"拍好了"，守卫把它**误判成假成功**并改写掉了。
一个守规矩的回答被当成违规处理 —— 比不拦更糟，因为它会训练人不信任守卫。

**修复思路：不看有没有那几个字，看这句话在不在"陈述"。**
按句子切开，命中下面任一条就不算声称：

- 句子里有 `？` / `?`（疑问句）
- 命中词后面紧跟 `没` / `吗` / `否`（"拍好了没"这种疑问式引用）
- 句子里有否定/条件/待办标记：不、没有、尚未、无法、不能、是否、吗、告诉、确认、如果、待

**教训**：任何基于关键词的守卫都要问一句"**这句话如果被复述一遍会怎样**"。
用户的问题里就带着那些关键词，而模型复述用户的话是最自然不过的行为。

这个回归已经写进自测（`selftest_nl.py` 第 12 组，4 条断言专门守它）。

### 6.4 列名拼错（`acked_at` vs `ack_at`）：工具层要"拒得说人话"

第 4 周的工具层查询 `commands` 表时用了 `acked_at`，实际列名是 `ack_at`。
因为工具层有统一异常兜底，它**没有崩**，而是返回了 `ok=false` 的结构化错误 ——
行为是对的，但如果错误信息是原始的 `no such column: acked_at`，
模型只会把它转述给用户，用户看到的是一句没用的技术报错。

**做法**：工具层的每类失败都给**面向语义**的错误文案，并附上"这是什么意思"：

| 失败 | 文案 |
|---|---|
| 设备不存在 | "根本没有这台设备（不在已知设备名单里）。**注意这与'设备存在但没有数据'是两回事**" |
| 查询为空 | "该条件下没有任何读数（注意：这是'查不到'，不是'设备没数据'）" |
| 参数不合法 | "limit 必须是整数，收到 'abc'" |
| 时间格式 | "时间参数无法识别：'昨天'（支持 10m / 2h / 3d 或 ISO 时间）" |

模型手里有什么样的错误信息，就会说什么样的话。**错误文案是提示词的一部分。**

### 6.5 为什么工具层要单独自测（不调模型）

模型的输出是**概率性**的：同一句话问两遍，措辞可能不一样，偶尔还可能不守规矩。
如果只靠"问模型看它答得对不对"来验证，就永远说不清"到底是代码错还是模型抽风"。

所以第 4 周拆成两层验证：

- **工具层（确定性）**：`selftest_nl.py`，21 组断言，**完全不调模型**。
  验的是"参数会不会被校验""非法设备会不会被拒""没有证据时 `success_claim_allowed` 是不是 false"。
- **模型层（概率性）**：命令行 + 网页实测，留人工记录（文档第十节）。

结论：**关键约束必须落在确定性的一层。**
"不许编数据"如果只写在提示词里，它就是概率性的；写在工具层和出口守卫里，它才是确定的。

### 6.6 编译通过 ≠ 行为正确：板端代码逐行审计抓出的 4 个问题（第 3 周）

`help_btn.c` 编译链接全过、逻辑看着自洽，但**从没在真机上跑过**。
所以提交前做了一遍逐行审计 —— 结果抓到 4 个问题，其中 1 个会让核心功能失效。

#### ① ★ 哨兵值当布尔用 →「VPS 已接收 = 常亮」这一档永远不亮

```c
/* 错 */
static int s_led_on = -1;                 /* -1 表示"刚切状态，需要强制重写" */
...
case LED_MODE_ON:
    if (!s_led_on) led_write(1);          /* -1 是真值 → 永远进不来 */
```

`s_led_on` 是个三态值（1=亮 / 0=灭 / -1=未知），但判断写成了布尔取反。
`-1` 在 C 里是真值，`!(-1)` 是 0，于是 **`HELP_ACCEPTED`（VPS 已接收）这个状态
永远不会点亮 LED** —— 而这恰恰是三层状态里"服务端那一层"唯一的物理反馈。

修复：改成显式比较 `== 1` / `!= 0` / `== -1`。
顺带发现 `LED_MODE_BLINK` 也有同样的隐患（第一个"亮"段被白等掉），一并修了。

> **教训：一个变量有两种以上含义时，绝不能当布尔用。**
> 这类 bug 编译不报、静态分析常常也不报，而它只在真机上表现为"某一档灯不亮"。

#### ② 在 esp_timer 回调里阻塞（vTaskDelay）

```c
static void tick_cb(void *arg) { ... help_btn_set_state(...); }   /* esp_timer 回调 */
void help_btn_set_state(...) { ... buzzer_pattern(st); }          /* 里面有 vTaskDelay */
```

`esp_timer` 的回调跑在它自己的高优先级任务里，**在里面阻塞会拖住整个定时器任务**：
轻则 LED 节拍乱掉，重则触发 task watchdog。

因为 `BUZZER_ENABLE` 默认是 0，这个问题**当时是休眠的** —— 一旦有人打开蜂鸣就炸。

修复：改成"独立任务 + 任务通知"。状态跃迁只做一次非阻塞的 `xTaskNotifyGive`，
真正的延时在蜂鸣任务里做。

#### ③ 「① 本地确认」在灯上根本看不见

原来的 `do_request()` 里是连着两句：

```c
help_btn_set_state(HELP_LOCAL_ACKED);   /* 慢闪：本地已确认 */
help_btn_set_state(HELP_SENDING);       /* 快闪：发送中 */
```

两句之间没有任何间隔，慢闪只存在几微秒 —— 用户只会看到快闪。
也就是说，三层状态里的**第①层在物理反馈上是不可观测的**，等于没做，
而文档里却写着"慢闪 = 本地已确认"。

修复：改成两段式。按下只做本地确认并"装填"待发内容，
真正的网络请求交给下一个主循环周期（约 0.5~1 秒后）。
用户因此能实实在在看到"板子收到我这一按了"，然后才转成"正在发"。

> **教训：一个状态如果在设计文档里有名字、在界面/物理反馈上却观察不到，那它等于不存在。**
> 这不是"实现不完整"，是"文档与行为不一致"，比前者更糟。

#### ④ 短按语义在 `FAILED` 状态下莫名其妙

原来：`s_pending = (s_state == HELP_IDLE) ? REQUEST : CANCEL;`
于是 `FAILED`（上次没发出去）状态下短按 → 去**取消**一条根本没送到服务端的求助，
服务端回 404，按键行为变得毫无规律。

修复：改成看"有没有活跃的求助"——
`IDLE / FAILED / CANCELLED / ANSWERED` → 发起新的；
`LOCAL_ACKED / SENDING / ACCEPTED` → 取消它。

#### ⑤ 顺带：非 200 时没排空响应体

`help_poll_viewer()` 只在状态码 200 时读 body，其他情况直接 close。
**不读干净就 close，协议栈会发 RST** —— 第 1 周在 `/api/ingest` 上踩过同一个坑，
表现为"服务端明明收到了，板子这边却报错"。已在 else 分支补 `drain_body()`。

---

**这一节最值得记的不是这 4 个 bug，而是它们是怎么被发现的：**

它们**编译不报、逻辑看着通顺、串口日志也会正常打印**。
唯一的发现方式是在"上真机之前"主动做一遍**逐行审计**，
并且带着一个问题读代码：**"这一行在真机上，用户能看到什么？"**

对 AI 生成/辅助生成的嵌入式代码，这一步不能省 ——
它能写出编译通过的代码，但"某一档灯永远不亮"这种事，
它自己不会知道，编译器也不会告诉你。

## 7. 第 5 周的坑（波形 / 姿态 / 时间轴）

第 5 周做的是"传感器示波器"：板端 20Hz 连续采样、攒批上传，
网页上画三轴波形 + 3D 姿态孪生。这一周的坑有个共同特征 ——
**它们全都编译通过、自测看着也绿，只有真机或者真渲染才露出来。**

### 7.1 ★ `or 默认值` 会吞掉合法的 0

```python
hz = int(data.get("hz") or 20)      # ← 错
```

`hz=0` 是**非法值**，本该被 400 拦下。但 `0 or 20` 的结果是 `20`，
于是"非法 0"被当成"没传"，一路畅通无阻地入库。自测当场抓到。

同一个写法在换算因子上更隐蔽：

```python
lsb_per_g = data.get("lsb_per_g") or 1024.0     # ← 同样错
```

板子如果报了个不合理的 `lsb_per_g=0`，本该"退回默认值**并如实告知**"，
但 `0 or 1024.0` 让它压根走不到那条告知分支 —— 于是永远不告警。

修复：显式区分"没有值"和"值是 0"。

```python
def num_or(raw_val, default):
    if raw_val is None or raw_val == "":
        return default          # 真的没传
    return float(raw_val)       # 传了 0 就老老实实拿 0 去校验
```

> **同一个病根在第 3 周的板端也犯过一次**（`s_led_on` 用三态 `-1` 表达
> "还没决定"，却被当成布尔用）。`-1` 是真值、`0` 是假值，
> 于是"还没决定"和"明确熄灭"在灯上完全一样 —— 结果是某一档灯永远不亮。
>
> **"没有值"和"值是 0"是两件事。** 这不是语法细节，是建模问题。

### 7.2 ★ 最优路径在真机上根本走不到

波形的时间轴要回答"样本之间隔多久"。第一版做了两条路：

1. 优先读**板端采样时刻** `t_last`（钟差是常数，两条时刻做差后自动抵消，所以是准的）；
2. 读不到就退回**服务端接收时刻**（含网络抖动，最差）。

自测全绿 —— 因为我造的数据里，板端时刻总是可解析的。

但**这块板子的 SNTP 实测经常对不上时**（第 1 周就记过），
此时板端时间戳写成 `uptime+12.345s(time_not_synced)`，**根本解析不出来**。
也就是说：**路径 ① 在这台设备上永远走不到，实际会掉到最差的路径 ②。**

补的第三条路是：

> **批号连续 + 采样率已知 → 完全不需要任何时钟，直接反推。**
> 每批 100 点 @20Hz = 5 秒，从最新一批往回累加即可。

并且加了一条自测断言：**反推出来的时间轴与"板子对时了"那条路逐点相同**。
两条互相独立的路算出一模一样的结果，才说明反推是可信的。

> **判断标准不该是"我的自测过了"，而应该是：
> 这条路径，在这台真设备上，到底会不会被走到？**
> 如果不会 —— 那这条最优路径是写给谁看的？
>
> 这是本周最值钱的一条。它和第 1 周"板子说失败、服务端说成功"是同一类问题：
> **别只看自己造的世界，要看真实世界会落到哪个分支。**

### 7.3 ★ 几何映射必须看渲染结果，不能只断言数值

3D 姿态孪生第一版用 `pitchCss = -asin(uy)` / `rollCss = asin(ux)`。

数值"全对"：平放算出来 0°、竖立算出来 ±90°。
但**画面是错的** —— 那两个角是**相对世界坐标系**算的，
却被塞进了一个已经被 `rotateX(58deg)` 转过的父层里。语义错位。

正确解法是**解一个方程**，而不是套公式：

```
求 R，使  R · g设备 = (0, 0, −1)      // 世界坐标系的"下"
```

两自由度刚好：

```js
var r1    = Math.sqrt(gx*gx + gy*gy);
var phi   = Math.atan2(gx, gy) * 180/Math.PI;       // 绕桌面竖轴
var theta = Math.atan2(r1, gz) * 180/Math.PI + 180; // 绕 X 轴压下去
plate.style.transform = 'rotateX(' + theta + 'deg) rotateZ(' + phi + 'deg)';
```

手工代入验证过：`g = (0.02, -0.71, 0.70)` → `R·ĝ = (0.0002, 0.0002, -0.9973)`，
确实是 `(0,0,−1)`。

> 有意思的是：**第三自由度（绕重力轴自转）本来就不可观测**，
> 所以平放时 `φ` 必然算出 0，孪生体也就不转 ——
> 这把"Yaw 测不到"从一句口号变成了**可验证的几何结论**。
> 自测里专门断言了这一条。

### 7.4 朝向文案判反：自测只查 key 是抓不到的

`uz > 0` 时我原写"正面朝上"，实际是"背面朝上"。
**所有数字都对、只有文案错** —— 自测当时只断言 `posture` 这个 key（`flat`），
怎么写反都能过。

改对之后还做了一件事：把这件事里**能确定的**和**只能假设的**分开写。

- **能 100% 确定**：静止时加速度计测的是**比力**（`f = a − g`，`a=0`），
  读数指向天空 —— 所以 `az > 0` ⟺ 传感器 +Z 轴朝上。与芯片怎么贴装无关。
- **只能假设**：+Z 对应板子的哪一面。乐鑫没公布，我们也没板子实测。

所以后者被提成一个显式常量：

```python
Z_UP_IS_FRONT_FACE = False   # 改这一行即整体翻转
```

并写了一条自测来验证"这句承诺没吹牛"：翻转常量后文案整体翻转，
而姿态分类 key 不变。

> **凡是"只能假设"的东西，就该摆在明面上、能一行改掉 ——
> 而不是埋在逻辑里，让下一个人猜为什么是反的。**

### 7.5 保留窗口清理器空转

自测报了三条 FAIL：清理后仍是 15 批、删掉 0 批。

根因：`WAVE_KEEP_BATCHES` 是**模块导入时**读的环境变量。
自测只在子进程的 `env` 里设了 3，自己 `import server` 进来的那份仍是 720 ——
于是清理器认为"没超窗口"，直接跳过。

修复：在 `main()` 开头（**import server 之前**）设好环境变量。

顺带把断言从"对比 `batch_seq`"改成"对比 **id 列表**" ——
批号可能因为清理而显得连续，id 不会骗人。

### 7.6 自测断言顺序错，误报成代码错

`selftest_page.js` 里有一条断言：

```js
check('平放时绕竖轴的角恒为 0', /rotateZ\(0\.0deg\)$/.test(els.twinPlate.style.transform));
```

它读的是**当前** `transform`，但它排在一个 `Tilted` 用例之后 ——
读到的是上一帧的 `rotateZ(45deg)`，于是报 FAIL。

**代码是对的，是断言的位置错了。**
修复：断言前重新渲染一帧平放。

> 教训：**测试自己也会骗人。** 看到 FAIL 先确认"测的是不是我以为的那个东西"，
> 别急着改被测代码。

### 7.7 预处理器不认识类型转换

```c
#define RING_SAMPLES   ((uint32_t)WAVE_RING_SAMPLES)   /* ← 错 */
#if (RING_SAMPLES & RING_MASK) != 0
```

`#if` 是预处理器表达式，**不认 C 类型转换**，报
`missing binary operator before token "512"` —— 而且**报错位置指向
`app_config.h`**，看着像配置文件写错了，实际是 `wave.c` 的问题。

去掉转换即可（`#define RING_SAMPLES WAVE_RING_SAMPLES`，在用到的地方再转）。

### 7.8 沙箱删不掉目录 + 旧进程占着端口 → 换端口最省事

起演示实例时 `rm -rf tmpdata_demo` 被沙箱拦下（`[safe-delete][SAFE_DELETE_FAIL_CLOSED]`），
而**旧进程还活着、仍在跑旧代码** —— 新接口一律 404 / `KeyError`，
看起来像"代码没生效"，其实是"根本没在跑新代码"。

- `taskkill //F //PID` 在 Git Bash 下报"无效参数"；
- 可用 PowerShell 的 `Get-NetTCPConnection -LocalPort N -State Listen | Stop-Process -Force`；
- 但 Windows 上 socket 可能被重复 bind，杀不干净。

**最省事的做法是换端口**（`tmpdemo2` → `tmpdemo3` → `tmpdemo5`，端口 8020 → 8021 → 8022）。

### 7.9 ★ 加了一张表，却忘了"同一个页面上的另一块功能"看不见它

第 5 周加完 `wave_batches`（姿态 + 波形）之后，接口齐了、网页画出来了、自测全绿 ——
**但同一个页面上的自然语言问答（第 4 周）看不见这块数据。**
表现是：

> 网页上画得出来的波形和姿态，用一句话问不出来。

这不是 bug，是**遗漏**。而遗漏比 bug 难发现得多，因为它**不报错**：
编译通过、自测全绿、页面上一切正常。

**根因是"只想到了新功能自己，没想到已有功能"**，具体漏了三处：

| 漏在哪 | 后果 |
|---|---|
| `known_devices()` 没扫 `wave_batches` | 只上传波形、没传 `readings` 的设备被判成**"根本没这台设备"**（而它正在正常上传） |
| 工具清单里没有相关工具 | 模型只能说"我查不到" |
| `SYSTEM_PROMPT` 里没写姿态的口径 | **查得到也会说错** —— 比如把"航向不可测"答成 `0°` |

第三处是这次的真正教训：**前两条是"能不能查到"，第三条是"查到了会不会说错"。**
而第三条恰恰是最容易漏的，因为它不在代码里、在**语义**里：

> 本板无陀螺仪/磁力计，**航向在原理上不可测**。

这句话只在文档里写了一遍，而**运行时模型看不见文档** ——
它只看得见工具返回的 JSON 和系统提示词。
所以结论是：**这类"原理上的边界"必须写进数据（`yaw: null` + `yaw_note`）
和提示词里，而不只是写在文档里。**

**这次是怎么发现并补上的**：做第 5 周收尾时主动回看"新加的数据，还有谁会用到"，
对照 `nl_agent.py` 的工具清单和 `known_devices()` 逐项比了一遍。

**可复用的检查清单 —— 加一张表（或一类新数据）时，同时问三件事：**

1. **白名单扫了吗？** —— 所有按 `device_id` 聚合的地方（设备列表、权限校验、歧义判断）
2. **工具/接口有了吗？** —— 对外暴露的每个入口
3. **口径写了吗？** —— 这块数据有哪些"只能这么理解"的约束？
   （哪些字段恒为 `null`、哪些值是估算、哪些状态不可互推、哪些会过期）

第 3 条列成清单，就是本项目一路攒下来的那些"不可互推"：
第 2 周 `UPLOADED ≠ COMPLETED`、第 3 周三层状态不可互推、
第 5 周 `dropped` 非 0 就不能反推时间轴、以及这次的"航向不可测 ≠ 没采到"。

---

**这一节最值得记的一句话：**

> 这一周所有的坑，**没有一个能被"编译通过"或"自测全绿"挡住**。
> 它们需要的是另外四种检查：
> **① 看真机会走哪个分支；② 看渲染出来的画面；③ 读自己写的断言在测什么；
> ④ 回看"新加的东西，还有谁该看见它"。**

## 8. 断网补传的坑（第 2 周欠账补做）

这一节记的是补做计划书 4.2「断网缓冲」时踩到的坑。
它们的共同点是：**都不是"写错了"，而是"写对了但漏了一处"或"定义了一个没人用的东西"。**

### 8.1 ★ 断网时 `continue` 跳过的是**整个循环体**，不只是上传

补做之前的写法：

```c
if (!s_wifi_connected) {
    ...
    ESP_LOGW(TAG, "Wi-Fi 仍未就绪，跳过本次上传");
    continue;          /* ← 注释说的是"跳过上传"，实际跳过了后面所有代码 */
}
```

注释写的是"跳过本次上传"，读起来完全合理。但 `continue` 作用于整个循环体，
后面**抓帧的代码也被跳过了** —— 断网那段时间一张图都没有。

**教训**：`continue` / `break` / `return` 这类跳转语句，注释要写清**它到底跳过了什么范围**，
而不是写"意图"。"跳过本次上传"这句话让人以为只影响上传，实际影响的是整轮。

补做时把抓帧缓存提到了主循环的**第 0 步**（所有上传逻辑之前），
并且刻意**不挂在传感器读取之后** —— 见 8.4。

### 8.2 ★ 同一个"旧值冒充"，换了个形状又出现一次

第 2 周的题眼是"证明板子进行了新采集，而不是显示旧值"。
断网补传把同一个问题摆回来了，但**形状完全不同**：

- 第 2 周：旧值在**服务端**（页面显示了数据库里的旧图）；
- 补传：旧值在**板子**（断网时拍的帧，联网后补传）。

而它比第 2 周更难发现，因为**补传帧和刚拍的帧长得一模一样** —— 都是一个 JPEG。

所以必须显式声明三件事，缺一条就会在画廊里出现"看起来属于某次请求的旧图"：

| 做法 | 缺了会怎样 |
|---|---|
| 带 `X-Source: backlog` | 服务端只能靠"有没有 `request_id`"猜来源 |
| 带 `X-Capture-Ts` = **采集时刻** | 前端把补传帧显示成"刚刚拍的" |
| **不带 `X-Request-Id`** | 被当成某次"现在拍一张"的观测，正是 E2 要拦的那个漏洞 |

**服务端对"补传 + `request_id`"的组合硬拒 400，而不是静默忽略。**
忽略看起来更宽容，但它会让两边对同一件事的理解不一致：
板端拿到 201 以为成功了，服务端悄悄丢掉了绑定关系。
这和"不能拿一个来源的事实去冒充另一个来源的事实"是同一条原则（第 3 周三层状态）。

### 8.3 ★ 定义了宏却没接线 —— 死开关

`app_config.h` 里写了 `BACKLOG_ENABLE 1`，但 `backlog.c` 和 `main.c` **都没读过它**。
于是它是个"看着有用、改了没用"的死开关 —— 比没有这个宏更糟，
因为它会让人以为关掉就生效了。

接线时有个细节：关掉时 `backlog_init()` **返回 `ESP_ERR_NOT_SUPPORTED` 而不是成功**。
返回成功的话，断网时日志会显示"已缓存一帧"而其实什么都没存 ——
那种"看起来在工作"的假象，比直接说"这个功能被关了"难排查得多。

**可复用的检查**：加一个配置宏之后，**搜一遍它被谁读过**。
如果只有定义处出现，那它就是个死开关。

### 8.4 ★ 一个子系统的故障，悄悄让另一个子系统也不工作

抓帧缓存第一版是放在 `qma7981_read()` **之后**的（因为"顺手"）。
但那里有一条：

```c
ret = qma7981_read(&s);
if (ret != ESP_OK) { ...; vTaskDelay(...); continue; }
```

于是**加速度计一旦读失败，整轮 `continue` 会把抓帧也停掉**。
串口上只看得到「读取传感器失败」，排查时根本想不到是它连累的。

这和 8.1 是同一个病根（`continue` 的作用范围比想象的大），
但表现不同：8.1 是"该做的没做"，这里是"**不相干的两件事被绑在了一起**"。

**判断方法**：把一段代码插进循环体时，先看**它前面有没有 `continue` / `return`**。
有的话，这段代码就会跟着那些早退一起被跳过。

### 8.5 队列顺序错掉是**静默**的

队列文件名用 `BBBBBB_SSSSSSSS_TTTTTTTT.jpg`（定长补零）保证字典序 == 先进先出。
如果哪天有人"顺手"把 `%06lu` 改成 `%lu`，队列顺序会乱，
但**编译通过、运行不报错** —— 只是补传按错的顺序发出去。

这类不变量在板子上肉眼很难发现，所以在主机上钉死了：
`selftest_backlog.py` 第 7 组会去读 `backlog.c` 的 `snprintf` 格式串，
与 Python 镜像**逐字符比对**，还带一条反例（不补零时 `"10"` 会排到 `"2"` 前面）。
谁改了 C 那边而忘了这里，这一组会红。

**同理**，第 8 组的 `BACKLOG_MAX_FRAMES` 也是从 `app_config.h` 读出来的，
不是写死的数字。

> 这两组**不是在跑固件代码**，而是"把固件里的约定写成可执行断言"。
> 文档里写清楚了这一点，不假装它测了固件。

### 8.6 解析文件名要卡"刚好用完整个名字"

`sscanf(name, "%6lu_%8lu_%8lu.%3s", ...) != 4` 这个判据**不够**：
`%3s` 读完 `jpg` 就停了，所以 `…_00000101.jpg_extra` 也会被判成合法。

它一旦混进队列，字典序可能永远最小 —— 于是每次补传都取它、每次都失败，
**整个队列永远卡在第一帧**（而且从日志上看，只是"补传一直失败"，
完全看不出根因在文件名解析）。

修法是加 `%n` 拿已消费长度，再跟 `strlen` 比：

```c
if (sscanf(name, "%6lu_%8lu_%8lu.%3s%n", &boot, &seq, &up, tail, &consumed) != 4)
    return -1;
if (consumed != (int)strlen(name))
    return -1;
```

**教训**：用 `sscanf` 校验格式时，**"能解析出字段"不等于"整个字符串符合格式"**。
要判完整匹配，必须额外确认"消费长度 == 总长度"。

### 8.7 顺带修的两处 README 内部不一致

同一次收尾里还发现 README 的排错小节编号重复了：
第 5 周的 15/16/17 和第 4 周的 15/16/17 撞号。已改成 18/19/20。

这类问题不影响运行，但**会让"第 15 条"这个指代失效** ——
而这份 README 里恰好有"见第 15 条"这种交叉引用。属于典型的"看起来没事、其实已经坏了"。

---

**这一节最值得记的一句话：**

> 补做欠账时最容易踩的不是"技术难"，而是**三类"看着没问题"的漏**：
> ① 跳转语句的作用范围比注释说的宽（8.1 / 8.4）；
> ② 定义了一个没人读的东西（8.3）；
> ③ 一条不变量被破了却不报错（8.5 / 8.6）。
> 这三类的共同点是：**它们都不会让编译失败，也不会让自测变红。**
