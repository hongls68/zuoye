## 二、本周唯一需要先想清楚的问题：姿态到底能不能只用加速度计判

**能。** 而且这不是"凑合能"，是**原理上正好覆盖**。

加速度计测的是什么？很多人以为是"重力方向"，严格说不是 ——
它测的是**比力**（specific force）：静止时 `f = a − g`，其中 `a = 0`，
所以读数指向**天空**，大小 1 g。

> 这一条顺带解释了一个常被当成巧合的现象：**静止时 |a| 恒为 1.000 g，与摆放姿态无关。**
> 参考实现那个姿态标签旁边的 `1.02G`，正是这个量 ——
> 也就是说**它的姿态分类也是拿重力方向判的**，和我们是同一个原理。

于是能测什么、不能测什么就一目了然了：

| 状态 | 能不能测 | 为什么 |
|---|---|---|
| 平放 / 竖立 / 侧立 / 自由倾斜 | ✅ | 都由"重力落在哪个轴"决定 |
| Roll（横滚）、Pitch（俯仰） | ✅ | 是设备**相对重力**的倾角 |
| **Yaw（航向）** | ❌ | 绕重力轴自转**不改变重力方向** —— 无论怎么转，重力还是指着同一面 |

要测 Yaw 必须用陀螺仪（积分角速度）或磁力计（找地磁北）。板上都没有。

所以界面上 Yaw 那一格写的是「**不可测**」而不是留空、也不是填 0°：

- 留空 → 会被当成"这一格没采到数据"，是**采集问题**；
- 填 0° → 会被当成"测出来是 0"，是**错误数据**；
- 写「不可测」+ 原因 → 才是正确表达：**这是原理上的边界，不是我们的疏漏**。

## 三、架构决定：为什么是「攒批上传」而不是「流式推送」

参考实现是 `~20Hz 实时推送`。要在我们的链路上做到那个形态，只有两条路：

| 方案 | 优点 | 代价 |
|---|---|---|
| **A. 批量上传**（采用） | 复用现有 HTTP 通道，**对丢包天然容错**（丢一批只少一段波形，不会把连接搞死） | 延迟一批（默认 5 秒） |
| B. 流式（WebSocket / MQTT） | 形态最接近参考实现 | 要在**实测延迟 3ms~770ms 剧烈抖动**的链路上多维护一条长连接 |

选 A。第 1 周就记过这条链路的脾气，第 2 周的命令通道也是因为这个才做成轮询的 ——
**在这条链路上，长连接是负担不是能力。**

一批 = `WAVE_HZ × (WAVE_BATCH_SAMPLES / WAVE_HZ)` 秒。默认 20Hz × 100 点 = **5 秒一批**。

## 四、数据流（板端 → 服务端 → 网页）

```
qma7981 (I2C)
   │  ① 20Hz 采样任务（wave.c，独立任务，vTaskDelayUntil 走自己的节拍）
   ▼
环形缓冲 512 点（≈25.6 秒）
   │  ② 攒够 100 点 → wave_take_batch()
   ▼
main 主循环 → POST /api/waveform（一批 100 点的原始 ADC 计数）
   │  ③ 服务端：入库 + 由重力方向算姿态/倾角
   ▼
wave_batches 表
   │  ④ GET /api/waveform（拼最近 N 批成连续波形）
   │     GET /api/attitude（只要最新一帧，孪生面板高频轮询用，比拉整条波形轻）
   ▼
网页：canvas 自绘示波器 + CSS 3D 姿态孪生
```

### 4.1 为什么采集和上传要分成两半

采样任务只负责"把样本塞进环形缓冲"，**不认识 HTTP**；上传放在 `main.c`。

不这样分的话，主循环里塞着的 HTTP 上传、摄像头抓帧、指令轮询，
随便哪一步慢一点都会把采样间隔拉歪 —— 而示波器的横轴正是靠这个间隔算出来的。

（和第 3 周的 `help_btn` 是同一个套路：**模块负责状态，主循环负责发请求**。）

### 4.2 三个具体的实现取舍

**① `vTaskDelayUntil` 而不是 `vTaskDelay`。**
后者是"干完活再等 50ms"，每轮实际间隔 = 50ms + 干活耗时，误差**一轮轮累加**；
前者是"到点就走"，周期不会被干活耗时带偏。

**② 环形缓冲满了丢最老的，不丢最新的。**
示波器要看的是"现在"，丢新样本等于画面卡住不动，比少一段更难看。

**③ 丢了就如实计数（`dropped` 字段），不抹平。**
这条见下一节 —— 它不是"顺手加的诊断字段"，而是**服务端能不能算出正确时间轴的前提**。

## 五、★ 本周最值得记的一件事：时间轴怎么摆

波形和别处的数据不一样：它要回答的是「**样本之间隔多久**」，
是个**相对间隔**，不是绝对时刻。

而这块板子的 SNTP 实测**经常对不上时**（第 1 周就记过），
板端时间戳会写成 `uptime+12.345s(time_not_synced)` 这种**不可解析**的串。

于是就有了三条路，按可信度排：

| 路径 | 怎么摆 | 什么时候能用 | 准不准 |
|---|---|---|---|
| ① `device` | 读板端采样时刻 `t_last` | 板端时刻可解析 | 准 —— **钟差是常数，两条时刻做差后自动抵消** |
| ② `derived` | **批号连续 + 采样率已知 → 直接反推** | 板号逐批 +1、同一次开机、批间无丢样本 | 准 —— **完全不需要任何时钟** |
| ③ `server` | 服务端接收时刻 `received_at` | 兜底 | **不准** —— 网络抖动会让间隔看起来不匀 |

> **路径 ② 是补上来的，而且它才是真机上会走的那条。**
> 第一版只做了 ① 和 ③。写自测时用的是我自己造的、板端时刻可解析的数据，
> 所以一路绿灯 —— 但真板子的 SNTP 常年对不上时，① 根本走不到，
> 实际会掉到最差的 ③。**"我造的演示数据好看，真设备反而退化"**，
> 这个坑值得单独记一笔（见 `项目复盘与踩坑记录.md`）。

三条路都**不违反**第 3 周那条铁律「服务端不采信板端报的时间」：

> 那条铁律管的是**判定** —— 入库时刻、证据校验、超时归因，一律仍用服务端时钟。
> 这里只是拿板端时刻摆**相对间隔**，而且用了哪条路、为什么，都在接口返回值里写明
> （`time_axis_source` / `time_axis_note`），网页上原样显示出来。

### 5.1 为什么 `dropped` 是这条链路上的一等公民

路径 ② 的前提是「批间没有丢样本」。所以：

- 板端环形缓冲溢出时会**如实计数**，随下一批报上来；
- 服务端只要看到 `dropped != 0`，就**不再反推**，退到路径 ③ 并说明原因；
- 批号断档（`1, 2, 5`）同理 —— 中间少了一批，累加就不成立。

自测里专门验证了：**路径 ② 反推出来的时间轴，与路径 ① 逐点相同**。
两条互相独立的路（一条读板钟、一条只用 n/hz）算出一模一样的结果，
才说明"板子没对时时反推的轴"是可信的，而不是"看着挺顺、其实差一点"。

## 六、接口清单（第 5 周新增）

### `POST /api/waveform` —— 板端批量上传一批采样

```json
{
  "device_id": "s3eye-group01",
  "sensor": "qma7981_accel",
  "boot_id": "a1b2c3-boot9",
  "batch_seq": 7,
  "hz": 20,
  "dropped": 0,
  "lsb_per_g": 1024.0,
  "calib": 0.8078,
  "t_first": "2026-09-23T09:00:00.000+08:00",
  "t_last":  "2026-09-23T09:00:04.950+08:00",
  "samples": [[17, -588, 580], "...共 100 组 [x,y,z]"]
}
```

| 字段 | 为什么必须有 |
|---|---|
| `samples` | **原始 ADC 计数**，不是换算后的 g。换算是可逆的 —— 服务端拿原始值可以按任意系数重算，反过来拿 g 值就永远回不到原始计数了 |
| `lsb_per_g` + `calib` | ★ **分开报，不合并**。以后要回答"这个偏差是量程选错还是零点没标"，两个都得在。只报一个融合后的 `scale` 就答不了 |
| `t_first` / `t_last` | 摆横轴用（见第五章） |
| `dropped` | 决定服务端能不能用路径 ② |
| `batch_seq` | 判断批与批之间有没有断开 |

返回 201，并**把算好的姿态回给板子**（`posture` / `acc_mag` / `pitch` / `roll`）。
板端把它打到串口 —— 现场演示时不用开网页就知道板子现在什么姿态；
网页显示不对时，能一眼看出是板端传错了还是服务端算错了。

脏数据一律 **400 拒收，不猜**：样本不是三元组、含非数值、计数超 int16、
单批超上限、`hz` 越界 —— 都直接报错。补个 0 蒙混过去只会把问题藏起来。

### `GET /api/waveform?device_id=X&batches=N`

把最近 N 批拼成一条连续波形。横轴是**相对现在的秒数**（负数往过去），
和参考产品那个 `-9s … 现` 一致。返回里带：

- `series{t, ax, ay, az}` —— 画图用的四个数组
- `time_axis_source` / `time_axis_note` —— **用了哪条路摆轴，网页原样显示**
- `latest` —— 最新一帧的姿态（不含 `samples`，太重）
- `batches_detail` —— 每批的批号/点数/丢样本数/姿态

### `GET /api/attitude?device_id=X`

只要最新一帧姿态。3D 孪生面板 800ms 轮询一次它，比拉整条波形轻得多。

## 七、板端配置（`firmware/main/app_config.h` 第 9 节）

```c
#define WAVE_ENABLE             1    // 1=启用波形采样；0=退回每秒一个点
#define WAVE_HZ                 20   // 采样率
#define WAVE_BATCH_SAMPLES      100  // 一批攒多少点（100/20 = 5 秒一批）
#define WAVE_RING_SAMPLES       512  // 环形缓冲（2 的幂，25.6 秒）
#define WAVE_UPLOAD_TIMEOUT_MS  8000
```

两个值得说的点：

**`WAVE_RING_SAMPLES` 必须保持 2 的幂。** 代码里用位与取模，不是 2 的幂会算错。
写了个编译期断言兜着（`#error`），配错时编译就过不去，不会拖到运行期。

**采样任务是在 Wi-Fi 就绪之后才启动的。** 环形缓冲只有 25.6 秒容量，
而连 Wi-Fi（最多 20s）+ 对时（最多 10s）加起来可能超过 25 秒 ——
那会儿就开始采，缓冲一开张就溢满，第一批报文直接带着 `dropped` 出门，
服务端就只能退回到最差的时间轴。这段时间本来也传不出去，早采没有意义。

## 九、一处必须说明的假设：哪一面朝上

加速度计读数里有一半是**能 100% 确定**的：

> 静止时它测的是"支撑力"（比力 `f = a − g`，`a = 0`），所以读数指向**天空**。
> 于是 **`az > 0` ⟺ 传感器的 +Z 轴朝上**。这一条与芯片怎么贴装无关。

另一半**只能假设**：

> "+Z 轴对应板子的哪一面"取决于芯片在板上的贴装方向。
> 乐鑫**没有公布**这个信息，我们手上也没有板子可以实测。

所以它被提成一个显式常量，摆在 `server.py` 最显眼的位置：

```python
Z_UP_IS_FRONT_FACE = False   # az>0 → 背面朝上（当前取值）
```

**数值照算，只有"哪一面朝上"这句文案跟着它变。**
拿到板子后平放一次 —— 看串口 `az` 是正是负、当时朝上的是哪一面，
若与约定相反，**改这一行即可，其余代码一行都不用动**。
自测第 3c 组就是在验证"这句承诺没吹牛"：翻转常量后文案整体翻转，
而姿态分类 key 不变。

> 当前取 `False` 的依据：本板平放时实测 `az ≈ +0.7`，
> 而参考产品把自己的平放态标成 `Flat Down（背面朝上）`，两者一致。

**为什么这个错特别难发现**：写反了的话**所有数字都对、只有文案错**。
自测若只断言 `posture` 这个 key，永远抓不到 ——
所以自测里连"说明文字里写没写明哪一面"也一起断言了。

## 十、保留策略：为什么波形和原图不能用同一个清理器

第 2 周做过原图的配额清理（`frame_purger`）。本周加波形时**没有复用它**，
而是另起了一个 `wave_purger`。理由：

| | 原图 | 波形 |
|---|---|---|
| 它是什么 | **证据** —— 回答"当时到底拍到了什么" | **过程** —— 回答"它刚才怎么动的" |
| 策略 | 元数据（含 SHA-256）**永久保留**，只清原图（7 天） | 留够复现窗口就行，老批**直接删**（每设备最近 720 批 ≈ 1 小时） |
| 周期 | 300 秒 | 60 秒 |

**合成一个清理器，早晚会把两条策略搅在一起** ——
要么波形把库撑爆，要么原图的哈希被一起删掉、证据就没了。
分清"什么是证据、什么是过程"，才不会一刀切地全留或全删。

## 十一、已知限制

1. **Yaw 没有** —— 原理上不可测，不是没做。要做得加陀螺仪/磁力计。
2. **延迟一批（5 秒）** —— 批量上传的固有代价。要看"此刻"，看网页上的数值条和孪生面板（它们走 `/api/attitude`，800ms 一次）。
3. **没有做 Wi-Fi 周边扫描** —— 扫描会让 STA 离开当前信道，**扫描期间正在传的数据会断**。要做也只能做成按需触发（点一下扫一次），绝不能定时轮询。本周没做。
4. **没有登录/鉴权** —— 裸接口。
5. **没有电量计** —— 板上没有 MAX17048。
6. **`lsb_per_g` / `calib` 是编译期常量** —— 换了板子要重新标定后重编译。
7. **时间轴路径 ② 依赖"批间无丢样本"** —— 链路抖动剧烈时 `dropped` 会不为 0，届时会退到路径 ③（并如实说明）。这是设计如此，不是 bug。

## 十二、这一周真正学到的东西

**"我造的演示数据好看，真设备反而退化"是一个必须主动去找的坑。**

时间轴那一版（只有 `device` / `server` 两条路）在自测里是全绿的 ——
因为我造的数据里板端时刻总是可解析的。但真板子的 SNTP 常年对不上时，
最优路径根本走不到，实际会掉到最差的那条。

判断标准不该是"我的自测过了"，而应该是：

> **这条路径，在这台真设备上，到底会不会被走到？**
> 如果不会 —— 那这条最优路径是写给谁看的？

补上路径 ② 之后，"板子没对时"这个**已知的常态**才第一次有了正确答案。
