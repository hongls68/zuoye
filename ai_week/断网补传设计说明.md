# 断网补传 —— 离线 Flash 缓存与恢复上传

> 对应《第二周作业-项目计划与四课实施方案（版本迭代稿）.md》4.2 节。
> 计划书里把这一条标成「**断网缓冲不是可选项**」，但它在 v1.1 落地清单里一直挂着 ❌，
> 直到本次补做。这份文档记录**为什么必须做、做的时候最容易错在哪、以及怎么验收**。

---

## 〇、一句话

摄像头抓帧**不需要网络**。断网时把帧先写进 Flash 队列，网络恢复后按先进先出补传 ——
但补传帧的采集时刻在**过去**，所以整条链路必须能回答"这一帧是现在拍的，还是几分钟前拍的"。

---

## 一、原来的漏，漏在哪

补做之前，主循环在断网时的写法是：

```c
if (!s_wifi_connected) {
    if (wifi_wait_connected(WIFI_RETRY_INTERVAL_MS)) {
        ...
    } else {
        ESP_LOGW(TAG, "Wi-Fi 仍未就绪，跳过本次上传");
        continue;            // ← 整轮循环体被跳过，连帧都没抓
    }
}
```

`continue` 跳过的是**整个循环体**，包括后面的抓帧代码。所以：

- 断网 5 分钟 → 这 5 分钟**一张图都没有**，网络恢复后也补不回来；
- 而抓帧本身（`camera_capture()`）根本不需要网络，这段能力被白白浪费了。

对一个"无人值守的采集终端"来说，这个行为是自相矛盾的：
设备脱网一段时间数据就永久丢失，那它就只能在网络好的时候才有用。

**修复后的位置**：抓帧缓存被提到主循环的**第 0 步**（所有上传逻辑之前），
并且刻意**不挂在传感器读取之后** —— 见第七节「两个子系统不该互相连累」。

---

## 二、题眼：补传帧的采集时刻在**过去**

第 2 周整周在防一件事：**"旧值冒充新采集"**。
当时的形状是"页面重新显示了数据库里的旧值"，所以设计了三道证据
（E1 `request_id` 贯穿 / E2 `capture_ts` 晚于下发时刻 / E3 同 `boot_id` 内 `seq` 递增）。

断网补传把同一个问题换了个形状又摆回来：

> 补传的帧和"刚拍的帧"长得**一模一样** —— 都是一个 JPEG。
> 但它的 `capture_ts` 是几分钟前。

所以三件事必须做全，缺一条就会在画廊里出现"看起来属于某次请求的旧图"：

| # | 做法 | 缺了会怎样 |
|---|---|---|
| ① | 带 `X-Source: backlog` | 服务端只能靠"有没有 `request_id`"猜来源，猜不出"这是补传的" |
| ② | 带 `X-Capture-Ts` = **采集时刻**（不是上传时刻） | 前端会把补传帧显示成"刚刚拍的"，三个时间口径塌成一个 |
| ③ | **不带 `X-Request-Id`** | 补传帧会被当成某次"现在拍一张"的观测，正是 E2 要拦的那个漏洞 |

### 服务端为什么**硬拒 400**，而不是"忽略掉 request_id 就好"

```python
if source == FRAME_SOURCE_BACKLOG and request_id:
    self._send_json({"error": "补传帧不能绑定 request_id", ...}, 400)
    return
```

忽略的做法看起来更"宽容"，但它会让两边对同一件事的理解不一致：

- 板端拿到 201，认为这次上传成功了；
- 服务端悄悄丢掉了绑定关系。

于是"这一帧到底属于谁"就成了一件**只有一边知道**的事。第 3 周那套
"三个来源不同的事实必须分列存"的道理在这里同样成立 ——
**能算准的一方来算，说不清的一方别猜**。既然入口就能拒，就不该让它进库。

> 顺带一提：这类帧就算进了库，E2 校验本来也会把它拦下（`capture_ts` 早于 `dispatched_at`）。
> 但那是**靠事后校验兜**。能在入口拒的，不该留给事后。

## 三、三个时间口径，一个都不能省

补传帧身上同时挂着三个"时间"，它们**回答的是三个不同的问题**，
所以必须分开存、分开显示，并且标明"这是谁的钟"：

| 字段 | 谁产生的 | 回答什么问题 | 能拿来判定吗 |
|---|---|---|---|
| `capture_ts` | 板端（`make_timestamp_ago`） | 这张图是**什么时候拍的** | ❌ 板子的钟，只作参考 |
| `buffered_us` | 板端（同一个单调钟相减） | 它在队列里**待了多久** | 仅作展示 |
| `ts_server` | 服务端（`now_iso()`） | 服务端**什么时候收到它的** | ✅ 判定用它 |

### 为什么 `buffered_us` 要由板端报，而不是服务端自己算

服务端当然可以算 `ts_server - capture_ts`，但那**依赖板钟走得准**。
板钟在 SNTP 对时之前是 1970 年，对时之后也可能偏。

而"在队列里待了多久"板端用**同一个单调钟**（`esp_timer_get_time()`）相减就能精确得到：

```
buffered_us = now_us - capture_uptime_s * 1000000
```

两个时刻都来自同一个钟，所以这个差值就是**真实经过的时间**，板钟准不准都不影响它。
这和第 5 周波形时间轴用的是同一套道理（见《第五周-传感器示波器与姿态孪生.md》）。

### 采集时刻怎么还原

补传时用 `make_timestamp_ago(buffered_us, ...)` 反推：

- **已对时** → 真实的 ISO 时刻，而且**必然是过去的时刻**（这正是它该有的样子）；
- **未对时** → `uptime+812.500s(time_not_synced)`，**原文保留**，服务端解析不出来会自己换一种摆法，
  绝不会把 `uptime+812.5s` 当成某个 1970 年的时刻。

关键在于：**板端 SNTP 常年失败**（见 README 的网络说明），
所以"未对时"这条路径不是兜底，而是**常态**。整段断网期间都没对时的话，
这帧"是多久以前拍的"信息也一点没丢 —— 因为它记的是 uptime 差值，不是墙上时间。

## 四、队列设计：文件名就是索引

### 为什么不用索引文件

索引文件意味着"两份数据要同时保持一致"。一旦在写索引时掉电，
队列就烂了（文件在、索引里没有；或者反过来）。而**文件名本身可以承载全部元数据**，
于是就没有这个不一致窗口：**文件写完了，这一帧就完整；没写完，名字根本不出现。**

SPIFFS 本身对掉电是安全的，所以这条路不需要我们自己处理半写状态。

### 文件名格式

```
BBBBBB_SSSSSSSS_TTTTTTTT.jpg
   │        │         └── 采集时刻的板端 uptime（秒）
   │        └──────────── 本次开机内的入队序号
   └───────────────────── 开机计数（NVS 里的 boot_cnt，单调递增）
```

**定长补零是故意的**：字典序排序就等于按 `(boot_cnt, seq)` 排序，也就是**先进先出**。
如果改成变长（`%lu` 不补零），`"10"` 会排在 `"9"` 前面，队列顺序就乱了 ——
自测第 7 组专门用一条反例把这个理由钉住。

`boot_cnt` 放在最前面，是因为**重启后 uptime 会归零**：
只有它能把"重启前攒下的帧"排在"重启后拍的帧"前面。

### 解析：必须"刚好用完整个名字"

C 侧用 `sscanf` + `%n` 拿已消费的字符数：

```c
if (sscanf(name, "%6lu_%8lu_%8lu.%3s%n", &boot, &seq, &up, tail, &consumed) != 4)
    return -1;
if (consumed != (int)strlen(name))
    return -1;                  /* ← 关键 */
```

只看 `sscanf` 返回 4 是不够的：`%3s` 读完 `jpg` 就停了，所以
`000001_00000001_00000101.jpg_extra` 这种"前缀像我们的名字、后面还挂着东西"的文件
也会被判成合法。它一旦混进队列，字典序可能永远最小 —— 于是每次补传都取它、
每次都失败，**整个队列永远卡在第一帧**。

### 已知限制（写出来，不假装没有）

开机计数超过 6 位（999999 次重启）或单次开机入队超过 8 位时，
文件名的定长字段会回绕，字典序不再等于 FIFO。实际使用中到不了，
但这是**文件名编码**这种做法的固有代价，所以在 `backlog.h` 和自测里都写明了。

## 五、参数取舍

| 宏 | 值 | 为什么是这个值 |
|---|---|---|
| `BACKLOG_OFFLINE_PERIOD_MS` | 10000 | 见下 |
| `BACKLOG_MAX_FRAMES` | 64 | 条数软上限；分区空间是硬上限，谁先到谁卡住 |
| `BACKLOG_MAX_FRAME_BYTES` | 200 KB | 单帧上限：超过就不入队，防止一张异常大的图吃满分区 |
| `BACKLOG_REPLAY_PER_LOOP` | 1 | 见下 |

### 离线抓帧为什么降到 10 秒（在线是 2 秒）

分区 3 MB，800×600 的 JPEG 一帧约 40~80 KB（估），装得下 35~70 帧。

| 间隔 | 覆盖窗口 | 结果 |
|---|---|---|
| 2 秒（沿用在线） | 约 1~2 分钟 | 断网 5 分钟只留下最后 1~2 分钟，**覆盖窗口反而更短** |
| 10 秒 | 约 6~11 分钟 | 时间上稀一点，但覆盖窗口够用 |

这是**有意的取舍**：宁可时间上稀一点，也不要覆盖窗口短到没意义。
真需要高密度就该换更大的分区，而不是把间隔调小。

> ★ 上表的窗口是按估算算的。真机上要实测一帧实际多大再复核。

### 每轮只补传 1 帧

每传一帧都要一次完整 HTTP 往返，本机这条链路抖动到 770 ms（见 README 网络说明）。
一轮里塞满补传，周期上报和命令轮询就被挤没了 ——
而"暂停周期上报后命令通道仍能出新数据"是课程明确的检查项，**为了补传把它挤挂是本末倒置**。

分开传的代价只是清空队列慢一点：离线按 10 秒攒、联网按约 2 秒一轮清，
清空速度本来就是积攒速度的 5 倍左右，队列不会越积越多。

### 和在线抓帧的关系

补传没清空完也**照常抓新帧**。两条流在画廊里是分开标注的
（补传帧有「断网补传」徽标和三个时间），所以时间上交错出现不会被误读成"板子时间乱了"。
刻意为它加一条"有积压就暂停抓新帧"的规则，反而会在网络差时
让画廊长时间看不到任何新画面 —— 那是更糟的结果。

## 六、诚实计数：丢了多少就说多少

这一节和第 5 周波形环形缓冲是**同一条原则**：用户关心"刚才发生了什么"，所以**丢最老**；
丢了就要报，不能抹平成 0。

| 规则 | 做法 | 不做会怎样 |
|---|---|---|
| 队列满 | 丢最老一帧，`dropped++` | 丢最新的，用户最关心的那几分钟反而没了 |
| 上报 | 每一帧带 `X-Backlog-Dropped` | 服务端以为数据完整，画廊不会提示"更老的帧已丢弃 N 帧" |
| 补传 | **先传成功再删** | 先删后传，传失败就等于凭空丢帧，而 dropped 还是 0 —— **比丢帧本身更糟**：它把"丢过数据"这个事实也一起丢了 |
| 写文件 | **检查 `fclose()` 返回值** | SPIFFS 的元数据在 close 时落盘，只看 `fwrite` 返回值会把"元数据没写下去"当成成功；写失败要 `unlink` 掉半成品 |
| 坏条目 | 取队首时发现就删掉 | 不删会永远卡在队首，**整个补传停摆** |

### 单帧过大为什么直接拒、不删老帧

删了也放不下（一张图就超过上限），只会白白丢掉一帧老数据。
所以 `backlog_put()` 对超限的单帧直接返回错误，让调用方如实记一笔。

## 七、分区与刷机

`firmware/partitions.csv`：

```
# Name,   Type, SubType, Offset,   Size,     Flags
nvs,      data, nvs,     0x9000,   0x6000,
phy_init, data, phy,     0xf000,   0x1000,
factory,  app,  factory, 0x10000,  0x300000,
backlog,  data, spiffs,  0x310000, 0x300000,
```

**`backlog` 刻意接在 `factory` 之后，不动前面的偏移。**
NVS 分区（Wi-Fi 凭据、`boot_cnt`）在 0x9000，如果把它往后挪，
刷机后就得**重新配网**，而且 `boot_cnt` 会重置 —— 队列文件名的第一段排序键就失去意义了。
多花 0 个字节就能避免这件事，没有理由不做。

### 两个子系统不该互相连累

抓帧缓存被放在主循环的**第 0 步**，而不是跟在 `qma7981_read()` 后面。
原因是后者有一条 `continue`：

```c
ret = qma7981_read(&s);
if (ret != ESP_OK) { ...; vTaskDelay(...); continue; }
```

如果抓帧缓存放在它后面，**加速度计一旦读失败，整轮 `continue` 会把抓帧也停掉**。
于是一个子系统的故障悄悄让另一个子系统也不工作，而串口上只看得到
「读取传感器失败」—— 排查时根本想不到是它连累的。

## 八、接口与代码位置

### 服务端（`server/server.py`）

| 接口 | 变化 |
|---|---|
| `POST /api/frame` | 解析 `X-Source` / `X-Buffered-Us` / `X-Backlog-Dropped`；**硬拒** `backlog + request_id` 的组合（400）；响应带 `backlog` 块 |
| `GET /api/frames` | 每条加 `is_backlog` / `buffered_us` / `buffered_s` / `backlog_dropped`；`storage` 加 `backlog_frames` / `backlog_dropped_total`；顶层加 `backlog_note` |
| `GET /api/ask`（第 4 周问答） | `query_frames` 工具同步这几个字段；`SYSTEM_PROMPT` 新增第 7 条铁律（补传的帧不等于"刚拍的"） |

```python
("buffered_us", "INTEGER"),      # 这一帧在 Flash 队列里待了多久
("backlog_dropped", "INTEGER"),  # 存它时队列已因满而丢弃的更老帧数
```

### 固件（`firmware/main/`）

| 文件 | 内容 |
|---|---|

| `main.c` | `frame_meta_t` 结构体；`upload_backlog_frame()`；`backlog_capture_if_due()`；`backlog_replay()`；主循环接线 |
| `app_config.h` | 第 10 节：`BACKLOG_*` 宏 |
| `partitions.csv` | 新增 `backlog` spiffs 分区 |
| `CMakeLists.txt` | SRCS 加 `backlog.c`；REQUIRES 加 `spiffs` |

### 为什么把 `upload_frame()` 的参数收成结构体

原来只有 `request_id` 一个可选参数，补传要再加三个，调用处会变成：

```c
upload_frame(buf, len, ts, ts, NULL, "backlog", -1, -1);
```

这种"数位置"的代码，**多一个参数就多一个传错的机会**。
结构体里字段有名字，传错会编译报错或一眼看出来：

```c
typedef struct {
    const char *request_id;       /* 命令触发时带；周期抓拍与补传都不带 */
    const char *source;           /* NULL=由服务端按有无 request_id 推断 */
    int64_t     buffered_us;      /* 补传：在队列里待了多久；<0 表示不适用 */
    int32_t     backlog_dropped;  /* 补传：存它时已丢了多少更老的帧；<0 不适用 */
} frame_meta_t;
```

`buffered_us` 用 `-1` 而不是 `0` 表示"不适用"，是因为 **0 也是一个合法的值**
（刚入队就传出去了）—— "没有值"和"值是 0"是两件事。

### 网页（`server/index.html`）

- 画廊卡片：补传帧打「断网补传」徽标，并把三个时间**分开写**
  （采集时刻 / 队列中待了 / 服务端收到），每行后面注明"这是谁的钟"；
- `backlog_dropped > 0` 时显示「更老的帧 已丢弃 N 帧（队列满）」；
- 统计条新增「其中断网补传 N」「补传期间丢弃 N」。

## 九、自测

`server/selftest_backlog.py` —— 9 组 72 条断言，自起隔离实例（`PORT=8016`），跑完自删。

| 组 | 覆盖 |
|---|---|
| 1 | 补传帧入库：三个时间口径分开；`capture_ts ≠ ts_server` |
| 2 | **硬拒** `backlog + request_id`（400），且**没有落盘、没有入库** |
| 3 | 补传帧不推进命令状态（`state` 仍 PENDING、`has_frame` 仍 false） |
| 4 | 不可信的值归 `None`；**`buffered_us=0` 是合法值**，不能归成 None |
| 5 | 未知 `source` 不拒收，但落库归成 `unknown` |
| 6 | 画廊单独标注 + 单独计数 |
| 7 | 队列文件名：字典序 == FIFO；**与 `backlog.c` 的格式串逐字符对账**；反例；解析边界 |
| 8 | 淘汰策略：满则丢最老、如实计数、**先传成功再删** |
| 9 | 老接口无回归 |

> 第 7、8 组是**把固件里的约定写成可执行断言**，不是在跑固件代码。
> 它们的价值在于：这两条不变量一旦破了，板子上是**静默出错**的
> （队列顺序乱掉不会报错，只会让补传按错的顺序发出去）。
> 第 7 组还额外读 `backlog.c` 与 `app_config.h` 做交叉对账 ——
> 谁改了 C 那边而忘了这里，这一组会红。

## 十、板上验收步骤

服务端侧已由自测覆盖，**固件侧必须在真机上验**（自测不能替代）。建议这样走：

1. **确认队列挂载成功**。串口应出现：
   ```
   断网缓存已挂载：总 3056 KB，已用 0 KB
   断网补传已就绪：分区 backlog，当前队列 0 帧，离线抓帧间隔 10000 ms
   ```
   若显示「断网缓存未启用（ESP_ERR_NOT_SUPPORTED）」，说明 `BACKLOG_ENABLE` 被关了。

2. **制造断网**。最省事的办法是**关掉路由器的 2.4G 频段**或把板子移出覆盖范围
   （不要改 `app_config.h` 重烧 —— 那会重置 `boot_cnt`，观察不到"重启前遗留"那条日志）。
   串口应开始出现：
   ```
   断网中：已缓存一帧到 Flash（队列 1 帧，累计丢弃 0 帧）
   断网中：已缓存一帧到 Flash（队列 2 帧，累计丢弃 0 帧）
   ```
   间隔约 10 秒。

3. **恢复网络**。串口应出现：
   ```
   Wi-Fi 已恢复
   补传缓存帧 000001_00000001_00001234.jpg（52341 bytes，采集于 128 秒前，队列还剩 2 帧）
   帧上传成功 (HTTP 201, 52341 bytes, seq=44)
   本轮补传 1 帧，队列还剩 1 帧
   ```
   注意 **`采集于 N 秒前` 会大于 0** —— 这就是"它不是刚拍的"的直接证据。

4. **网页核对**。画廊里应出现带「断网补传」徽标的卡片，
   **采集时刻**明显早于**服务端收到**，**队列中待了**与串口打印的秒数对得上。
   统计条「其中断网补传」应等于补传帧数。

5. **验"补传帧不能冒充命令观测"**。断网期间从网页下发一条采集指令，
   等它超时（`TIMEOUT`）；恢复网络后，这条指令**不应该**因为补传帧而变成 `COMPLETED`，
   `has_frame` 应仍为 false。

6. **验队列上限与诚实计数**（可选，耗时较长）。断网足够久让队列写满，
   串口应出现丢弃计数；恢复后画廊显示「更老的帧 已丢弃 N 帧」。

## 十一、已知限制与没做的事

| 项 | 说明 |
|---|---|
| 覆盖窗口是估算值 | 6~11 分钟按单帧 40~80 KB 估的，**真机需实测一帧实际多大**再复核 |
| 文件名定长字段会回绕 | 开机计数超 6 位或单次开机入队超 8 位时字典序不再等于 FIFO（见第四节） |
| 采集时刻是秒级 | 文件名里只存秒。补传帧不参与任何命令闭环，秒级足够；**不当成"精确到毫秒"** |
| 补传不做去重 | 若服务端已收到某帧但响应丢失，板端会重传一次，画廊里会出现两张一样的图（`sha256` 相同）。**没有做去重**：宁可有重复，也不要因为"以为收到过"而漏掉一帧 |
| 未在真机上跑过 | 本机没有可用的板子（板子常处于脱机供电状态，无 COM 口）。固件已编译通过（0 警告 0 错误），**行为验收要按第十节在板上走一遍** |
| 补传不做带宽自适应 | 网络差时清空队列会慢，但不会更糟 —— 反正帧已经在 Flash 里了 |
