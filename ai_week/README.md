# AI交互课 · 开发板 → 服务器 → 网页 完整数据链路

一套最小但完整的物联网系统：**ESP32-S3-EYE 板载加速度计采集真实数据 → 通过 Wi-Fi 上传到自建服务器 → 服务器存储并提供查询接口 → 浏览器网页实时展示**。

本文件是这套系统的**部署入口**，同时覆盖两个阶段的功能：

| 阶段 | 功能 | 数据方向 | 对应章节 |
|---|---|---|---|
| 第 1 周 | 板子**主动**周期上报传感数据与图像，网页被动展示 | 设备 → 服务器 | 一 ~ 五、七 |
| 第 2 周 | 网页**主动**下发拍照指令，板子执行并回传证据链 | 服务器 → 设备 → 服务器 | 五、六 |

第 2 周不新建工程，而是在同一套固件与同一个服务端上**增量叠加**命令通道；
两个阶段共用一份 `server.py`、一份 `main.c`，通过 `app_config.h` 的宏开关可随时退回纯第 1 周形态。

## 二、硬件说明（重要，和你的板子直接相关）

| 项目 | 值 | 说明 |
|---|---|---|
| 开发板 | ESP32-S3-EYE | 乐鑫官方 AI 开发板 |
| 传感器 | **QMA7981** 三轴加速度计 | **板载自带，无需外接 MPU6050** |
| I2C 引脚 | SDA = GPIO4，SCL = GPIO5 | 板载连线，固件已写死 |
| I2C 地址 | 0x12 | AD0 接地 |
| 串口 | **COM4** | 芯片原生 USB Serial/JTAG，非 USB 转 UART 桥接 |
| 芯片 MAC | 94:A9:90:1C:6F:F8 | 可用于核对"数据确实来自本组设备" |

> 老师允许"使用上学期的任何带 IMU 传感器的开发板"——ESP32-S3-EYE 板载 QMA7981，本身就满足"带 IMU"的要求，不需要额外接线。

**量程设置为 ±8g，灵敏度 1024 LSB/g**（依据 QST 原厂数据手册 Rev.A 第 20 页 RANGE 表）。选 ±8g 而非 ±2g，是因为手持板子做"拿起、倾斜"动作时瞬时加速度会超过 2g，量程太小会削顶导致数据失真。

## 三、部署步骤

### 第 0 步：日常想直接跑起来（最快）

已经烧录过、只是想看数据时，**双击项目根目录下的 `start-server.bat`** 即可：

- 它会自动启动服务端，并打开浏览器到 `http://127.0.0.1:8000/`
- 服务端在**新弹出的黑窗口**里运行，那里会打印局域网 IP
- 要停止：关掉那个黑窗口（或在里面按 `Ctrl+C`）

> 板子插着并联网时，网页会自动刷新出实时数据；
> 板子没插时，网页会保留最后一条记录并显示黄色「数据未更新」提示 ——
> 这正是老师检查项 2 的预期表现，不是故障。

下面是第一次部署 / 重新烧录时的完整步骤。

### 第 1 步：启动服务端（你的电脑当服务器）

```powershell
cd D:\zuoye\ai_week\server
python server.py
```

启动后会打印两行地址：

```
本机访问:  http://127.0.0.1:8000/
局域网访问: http://192.168.x.x:8000/   ← 这个地址要抄进固件
```

**把"局域网访问"那个完整地址抄下来**，下一步要用。

> 服务端只用 Python 标准库（http.server + sqlite3），无需 pip 安装任何东西。

### 第 2 步：放行 Windows 防火墙（必须做，否则板子连不上）

板子要从局域网访问你电脑的 8000 端口，默认会被防火墙拦住。任选一种方式：

- **方式 A（图形界面）**：设置 → 网络和 Internet → Windows 安全中心 → 防火墙和网络保护 → 允许应用通过防火墙 → 找到 Python 勾选"专用"和"公用"。
- **方式 B（命令行，需管理员权限）**：
  ```powershell
  New-NetFirewallRule -DisplayName "IMU Ingest 8000" -Direction Inbound -Protocol TCP -LocalPort 8000 -Action Allow
  ```

### 第 3 步：填写固件配置

用记事本或 VS Code 打开 `firmware\main\app_config.h`，填三处：

```c
#define WIFI_SSID       "你的WiFi名称"          // 必须是 2.4GHz，且和电脑同一个网络
#define WIFI_PASSWORD   "你的WiFi密码"
#define SERVER_URL      "http://192.168.x.x:8000"  // 第1步抄下来的局域网地址
#define DEVICE_ID       "s3eye-group07"         // 换成你的组号或学号
```

> **Wi-Fi 密码请自己在本机填写，不要发给任何人（包括 AI 助手）。**

同一文件里还有一个**摄像头开关**（可选增强功能，默认开启）：

```c
#define CAMERA_ENABLE   1    // 1=启用板载 OV2640 摄像头；0=退回纯加速度版本
```

保持 `1` 即为「加速度上报 + 摄像头实时传图」；改成 `0` 后重新编译，固件行为与不含摄像头时完全一致。
摄像头的方案、接线与代码说明见 [`摄像头功能方案与Git提交.md`](摄像头功能方案与Git提交.md)。

### 第 4 步：编译并烧录

```powershell
# 打开 ESP-IDF 命令行（开始菜单搜 "ESP-IDF 5.5 PowerShell"）
cd D:\zuoye\ai_week\firmware

idf.py set-target esp32s3      # 仅首次需要
idf.py build                   # 编译
idf.py -p COM4 flash           # 烧录到板子
idf.py -p COM4 monitor         # 打开串口监视器看日志（退出按 Ctrl+]）
```

### 第 5 步：看网页

浏览器打开 `http://127.0.0.1:8000/`，应当看到三轴加速度实时跳动；
若 `CAMERA_ENABLE=1`，页面还会显示摄像头实时画面（每 2 秒一帧，取自 `GET /api/frame/latest`）。

## 四、如何验证"数据是真的"（老师课堂要检查的三项）

### 检查项 1：倾斜板子，三处数值必须一致

板子平放静止时，重力全部落在某个轴上，该轴应约为 **1.000 g**，另外两轴约为 0。
倾斜板子，三个值会跟着变。三处对照：

| 位置 | 怎么看 |
|---|---|
| **板端** | `idf.py -p COM4 monitor` 的串口日志，形如 `raw: x= 12 y= -8 z= 1020 \| g: ax=+0.012 ay=-0.008 az=+0.996` |
| **服务器** | 运行 `python 三处对账核对.py`，或直接查 `/api/latest?device_id=你的设备编号` |
| **网页** | `http://127.0.0.1:8000/` 页面上的三个大数字；卡片下方还有原始 ADC 计数，历史表含「原始ADC (x/y/z)」列 |

三者数值必须对得上（网页显示 3 位小数）。

### 检查项 2：停止采集，网页必须保留旧值并提示未更新

拔掉板子 USB，或按板子上的 RST 键。**网页不能变空白、不能显示 0、不能继续跳假数**，而应：
- 保留最后一条记录的数值和时间戳；
- 状态变为黄色 **"数据未更新：最后一条采集于 …（N 秒前），开发板可能已停止上传"**，N 会持续增长。

判定阈值是 10 秒（网页内 `STALE_MS`），因为上传周期是 1 秒，10 秒没新数据必然说明停了。

### 检查项 3：数据确实来自本组设备，页面无写死数值

- 网页显示的设备编号 = 你在 `app_config.h` 里填的 `DEVICE_ID`；
- 串口日志会打印板子 MAC（`94:A9:90:1C:6F:F8`），可与设备管理器里 COM4 的属性对照；
- `index.html` 里所有数值都来自 `/api/latest` 与 `/api/history` 接口，源码中搜不到任何固定加速度数值；
- 数据库可独立核验：`python -c "import sqlite3;print(sqlite3.connect('data.db').execute('select * from readings order by id desc limit 5').fetchall())"`

## 五、服务器接口一览

### 5.1 第 1 周：设备主动上报（数据自下而上）

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/ingest` | 开发板上传一条记录 |
| GET | `/api/latest?device_id=X` | 查某设备最新一条 |
| GET | `/api/history?device_id=X&limit=N` | 查历史记录（新→旧，N 上限 200） |
| GET | `/api/devices` | 列出所有上报过的设备及最后上报时间 |
| POST | `/api/frame` | 开发板上传一帧 JPEG（`CAMERA_ENABLE=1` 时每 2 秒一次，单帧上限 1 MB） |
| GET | `/api/frame/latest?device_id=X` | 取某设备最新一帧 JPEG（网页 `<img>` 直接引用） |
| GET | `/api/health` | 服务自检 |
| GET | `/` | Web 展示页面 |

上传的 JSON 字段：`device_id`、`sensor`、`unit`、`ax/ay/az`（换算并标定后的 g）、`ax_raw/ay_raw/az_raw`（原始 14 位 ADC 计数，**未作标定**，与板端串口日志完全一致，用于对账）、`is_new_sample`、`time_synced`、`ts_device`（板端时间）。服务器入库时额外打上 `ts_server`。

摄像头走独立通道：`POST /api/frame?device_id=X`，请求体是**原始 JPEG 字节流**（不是 JSON），成功返回 201。
服务器把最新一帧落盘到 `server/snapshots/`，`GET /api/frame/latest` 直接回该 JPEG 供网页 `<img>` 显示。

> 以上字段**全部落库**（`readings` 表）。早期版本仅存 ax/ay/az，原始值在入库时被丢弃，
> 导致服务器侧无法与板端对账；现已补齐。已存在的旧库会在服务启动时自动 ALTER 加列，历史数据不丢。

### 5.2 第 2 周：网页主动下发指令（数据自上而下）

| 方法 | 路径 | 调用方 | 用途 |
|---|---|---|---|
| POST | `/api/command` | 网页 | 下发一条采集指令，返回新生成的 `request_id` |
| GET | `/api/command/poll?device_id=X` | 开发板 | 板子每 5 秒轮询一次，取走待执行指令（取走即置 `RECEIVED`） |
| POST | `/api/command/ack` | 开发板 | 板子回执执行状态（`EXECUTING` / `FAILED`），携带 `boot_id`、`seq` |
| GET | `/api/command/status?request_id=X` | 网页 | 查指令当前状态与时间线（不传 `request_id` 时按 `device_id` 列最近 N 条） |
| GET | `/api/command/frame?request_id=X` | 网页 | 取**本次请求**对应的那张图 |

**指令状态机**

```
PENDING ──取走──► RECEIVED ──回执──► EXECUTING ──帧到达──► UPLOADED ──证据齐全──► COMPLETED
   │                  │                  │
   │ TTL 内无人取      │ 执行超时          │ 执行超时
   ▼                  ▼                  ▼
EXPIRED            TIMEOUT            TIMEOUT          （设备显式报错 → FAILED）
```

两条必须记住的规则：

1. **`UPLOADED ≠ COMPLETED`**。帧到达只是"收到图了"，还要过证据校验（见下）才算 `COMPLETED`。
2. **超时不判硬件故障**。`PENDING` 超时说明**没人来取**（设备关机/掉线），记 `EXPIRED`；
   `RECEIVED`/`EXECUTING` 超时说明**设备已接手但没干完**，记 `TIMEOUT`。
   两者的排查方向完全不同，混为一谈会误导排障。

**三条证据（缺一不可，服务器自动校验）**

| 编号 | 判据 | 拦住的作弊方式 |
|---|---|---|
| **E1** | 观测记录携带的 `request_id` 必须等于本次指令的 `request_id` | 随便传一张与请求无关的图 |
| **E2** | 观测的 `capture_ts` 必须**晚于**指令的 `dispatched_at` | 把数据库里的旧图重新提交一遍 |
| **E3** | 同一 `boot_id` 内 `seq` 必须**严格递增** | 同一张图重传冒充新拍 |

**防"旧值冒充"的两道闸（本课重点）**

- `/api/command/frame` **只返回本次请求的那张图**；请求未完成时返回 **404**，
  **刻意不回落**到 `/api/frame/latest` 的最新图 —— 一回落，"旧值冒充"就成立了。
- 指令状态字段 `has_frame` 仅在 `state == COMPLETED` 时为 `true`。
  未完成时网页显示"等待中/未完成"占位，并且**主动清掉 `<img>` 的 `src`**，不留上一张图在屏幕上。

**与周期上报解耦**：命令通道走独立的 5 秒轮询计时，不受周期采集/上报是否暂停影响。
课堂上把网页的"暂停"按钮按下去之后，远程采集**依然可用** —— 这本身就是一条可展示的证据。

### 5.3 第 2 周：照片画廊与数据配额

| 方法 | 路径 | 调用方 | 用途 |
|---|---|---|---|
| GET | `/api/frames?device_id=X&limit=N` | 网页 | 画廊元数据列表（新→旧，N 上限 500），附存储统计 |
| GET | `/api/frames/image?id=N` | 网页 | 按帧 id 取**原图**；已被配额清理的帧返回 404 + `sha256` |

**保留策略（计划书 4.5）**：**元数据永久保留，原图按配额清理**。

- 每帧入库时记下 `sha256`、`size_bytes`、`width`、`height`、`source`（`web_manual` / `periodic`）。
- 后台线程每 5 分钟扫一次，把超过 `RETENTION_DAYS`（默认 **7 天**，可用环境变量覆盖）
  的原图文件删掉并置 `purged_at`；**数据库里的那一行与哈希一条都不动**。
- 所以画廊里"已清理"的帧依然在列，依然能读到拍摄时间与 SHA-256。
  **图片可以过期，证据不过期** —— 这就是哈希留痕的意义。
- `sha256` 也能回答一个很实际的提问：「这一帧和刚才那帧，是不是同一张图？」

页面上对应「照片画廊」区块：缩略图卡片墙，每张卡片带来源徽标（网页指令 / 周期抓拍）、
状态徽标（在库 / 证据齐全 / 原图已清理）、帧号、分辨率、大小、拍摄时间、所属 `request_id`
与 SHA-256 前 16 位；点击缩略图可放大原图（Esc 关闭）。

自测：`python selftest_gallery.py`（**自起隔离实例**，把 `RETENTION_DAYS` 压到 0 强制过期，
覆盖哈希落库、画廊列表、按 id 取图、清理后元数据与哈希仍在、已清理帧返回 404 等 20 项断言）。

## 六、第 2 周：远程下发拍照指令的课堂验证

第 2 周的题眼只有一句话：**怎样证明开发板进行了新采集，而不是页面重新显示了数据库里的旧值？**

因此本节的验证重点不是"能不能拍到图"，而是"能不能拿出证据说明这张图是刚拍的"。
按下面四步走，每步都留下可截图的结果。

### 第 0 步：不接板子先跑一遍状态机自测

自测脚本打的是**已经在跑的服务端**（默认 `http://127.0.0.1:8000`），
所以需要开两个终端：一个跑服务端，一个跑自测。

```bash
# 终端 1
cd server && python server.py

# 终端 2（服务端起来之后再跑）
cd server && python selftest_command.py
```

若服务端换了端口，把地址作为参数传进去：

```bash
python selftest_command.py http://127.0.0.1:8010
```

它用一套**独立的虚拟设备号**（`selftest-device-<时间>-<pid>`）发请求，
不会干扰你真实板子的记录；但如果指向的是你的主服务端，`data.db` 里会多出这些自测指令行，
介意的话可以先用独立数据目录起一个服务端：

```bash
# 终端 1（隔离实例，端口与数据目录都与主服务端分开）
set PORT=8010 && set DATA_DIR=./tmpdata && python server.py
# 终端 2
python selftest_command.py http://127.0.0.1:8010
```

脚本用假 JPEG 走完 5 个场景共 25 项断言：

| 场景 | 验证内容 |
|---|---|
| 1 正常闭环 | 下发 → 取走 → 回执 → 传帧 → 证据齐全 → `COMPLETED` |
| 2 设备关机 | 指令一直没人取，TTL 到期转 `EXPIRED` |
| 3 重复点击 | 两次点击生成两个不同 `request_id`，互不干扰 |
| 4 旧值冒充 | 传一帧 `capture_ts` 早于下发时刻的图，被 **E2** 拦下 |
| 5 重复上传 | 同一 `boot_id` 内 `seq` 不递增，被 **E3** 拦下 |

期望输出结尾为 `25/25 通过`。**这一步失败就不用往下走了**，先修服务端。

### 第 1 步：暂停周期上报，确认命令通道仍然活着

1. 板子上电，网页能看到加速度数值在跳；
2. 点网页上的**暂停**按钮 —— 数值停止刷新，状态显示"未更新"；
3. 此时点**远程采集**。

能拍到图，就证明命令通道与周期上报是**解耦**的：板子不是靠"每 2 秒本来就要拍"来应付指令的。

### 第 2 步：核对 `request_id` 贯穿三处

一次成功的远程采集，同一个 `request_id` 必须同时出现在三个地方：

| # | 位置 | 怎么看 |
|---|---|---|
| ① | **指令记录** | 网页「请求记录」表首列，或 `sqlite3 data.db "select request_id,state from commands"` |
| ② | **设备回执** | 服务端控制台会打印 `收到回执 req-xxxx（state=..., boot_id=..., seq=...）` |
| ③ | **观测记录** | 服务端控制台打印的校验结论，或 `sqlite3 data.db "select request_id,capture_ts,boot_id,seq from frames"` |

三者对不上，说明链路上有一环是"看起来对"而不是"真的对"。

### 第 3 步：验证证据校验真的会拦人

课堂上最值得演示的是**主动造一次假，看服务器拦不拦得住**：

```bash
# 拿一条已 COMPLETED 的 request_id，手工提交一帧 capture_ts 早于下发时刻的图
curl -X POST "http://127.0.0.1:8000/api/frame?device_id=<你的DEVICE_ID>" \
     -H "X-Request-Id: <该 request_id>" \
     -H "X-Capture-Ts: 2020-01-01T00:00:00+08:00" \
     -H "X-Boot-Id: fake-boot" -H "X-Seq: 999" \
     --data-binary @server/snapshots/<任一 jpg>
```

服务端应回 `evidence_ok=false`，理由含 **`E2 不通过`**，且该指令**不会**变成 `COMPLETED`。

### 第 4 步：验证"未完成时页面不显示旧图"

下发一条指令后，在板子响应之前（或干脆把板子关机）观察网页：

- 状态徽标是灰/黄，文案为"等待中"或"未完成 · 已过期"；
- 图像区显示的是**占位文字**，不是上一张成功的照片；
- 直接访问 `/api/command/frame?request_id=<该指令>` 应返回 **404**。

这三条同时成立，才说明"旧值冒充"这条路被彻底堵死了。

## 七、故障排查（按发生频率排序）

### 1. 串口监视器什么都不打印
`sdkconfig.defaults` 已设 `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y`。若仍无输出，先确认 `idf.py set-target esp32s3` 执行过，且 monitor 指向 COM4。

### 2. 板子连不上 Wi-Fi
- **最常见**：连的是 5 GHz 网络。ESP32-S3 **只支持 2.4 GHz**，必须在路由器上确认有 2.4G 频段并连它。
- **校园网/公司网开了 AP 隔离**：设备之间无法互访，板子 ping 不通你电脑。解决办法是用手机开热点，让电脑和板子都连手机热点。
- 认证方式不匹配：默认配置接受 WPA2 及以上。若是 WPA3 网络，把 `main.c` 中 `WIFI_AUTH_WPA2_PSK` 改为 `WIFI_AUTH_WPA3_PSK`；企业级 802.1X 认证本固件未实现。

### 3. Wi-Fi 连上了，但上传失败
日志会打印 `上传失败: ESP_ERR_HTTP_CONNECT` 之类。依次检查：
- `SERVER_URL` 填的是**局域网 IP**（192.168.x.x），不是 127.0.0.1——板子看 127.0.0.1 是它自己；
- 服务端 `python server.py` 是否在运行；
- 防火墙是否放行了 8000 端口（第 2 步）；
- 电脑 IP 是否变了（DHCP 重新分配后 IP 会变，要重新填 `SERVER_URL` 并重新编译烧录）。

### 4. 三轴数值明显不对（比如平放时不是 1g）
先看串口日志的 `raw` 原始值。若原始值正常但换算后不对，是 `QMA7981_LSB_PER_G` 与实际量程不匹配，按对照表改 `app_config.h`：±2g→4096、±4g→2048、±8g→1024、±16g→512、±32g→256，改完重新编译烧录。

### 5. 烧录失败 / 板子反复重启后烧不进去
这块板没有 USB 转 UART 桥接芯片，官方文档明确记载了这个已知问题。救法：
**按住 BOOT 键 → 再按 RST 键 → 松开 RST → 松开 BOOT**，板子进入下载模式，然后重新 `idf.py -p COM4 flash`。烧完按 RST 启动程序。

### 6. COM4 消失了 / 识别不到设备
优先怀疑 USB 线：很多 Micro-USB 线是**只充电不传数据**的，外观完全一样但内部少两根线。换板子原装线或确认能传文件的线，并直插机箱后置 USB 口，不要用扩展坞。

### 7. 数值超量程 / 平放时不是 1g（先看合成加速度）
先算 **|a| = √(ax²+ay²+az²)**。板子静止时它应恒为 **1.000 g** 左右，与摆放姿态无关。
这是判断数据是否可信的第一指标，比对单个轴有效得多。

| 现象 | 原因与处理 |
|---|---|
| **\|a\| 远大于 1（如 20+）** | 驱动未对 14 位补码做符号扩展，负值被当大正数。查 `qma7981.c` 的 `qma7981_compose()` |
| **\|a\| 稳定在 0.9 左右** | 传感器灵敏度误差，按 `app_config.h` 中 `QMA7981_CALIB_SCALE` 注释重新标定 |
| **\|a\| 随摆放姿态明显变化** | 存在零点偏移，需六面法校准；课程作业一般针对平放姿态整定系数即可 |
| **单轴接近 ±8（满量程）** | 量程设置与实际不符，核对 `QMA7981_RANGE_BITS` 与 `QMA7981_LSB_PER_G` 是否成对匹配 |
| **\|a\| 在 1 附近但抖动大** | 板子未放稳或有振动；标准差 < 0.02 才算静止 |

### 8. 开了摄像头之后，加速度数据也一起不传了

这是**摄像头抢 I2C 总线**的典型症状，不是传感器坏了。
`esp_camera_init` 默认会在 **I2C 端口 1** 新建 SCCB 总线，引脚却仍指向 GPIO4/5，与 QMA7981（端口 0，同为 GPIO4/5）争抢同一对物理线，
导致加速度计读取失败 → 主循环 `continue` → **两类数据全部停止上传**。

修法（见 `firmware/main/camera.c`）：把 SCCB 引脚设为 `-1`，并指定 `.sccb_i2c_port = I2C_NUM_0`，让摄像头**复用**加速度计已建好的总线。
若暂时不需要摄像头，把 `app_config.h` 的 `CAMERA_ENABLE` 改成 `0` 重新编译，即可恢复纯加速度版本。

### 9. 点了「远程采集」，指令一直停在"等待中"（PENDING）

说明**板子根本没来取**。按顺序查：

- 板子是否在跑？串口日志里应每 5 秒出现一次轮询痕迹（或看服务端有没有收到 `/api/command/poll` 请求）；
- `CMD_ENABLE` 是否为 `1`（`app_config.h` 第 7 节），改成 `0` 就整条命令通道都关掉了；
- 网页左上角选的设备编号，与 `app_config.h` 里的 `DEVICE_ID` **是否完全一致** —— 这是最常见的原因，多一个空格都不行；
- 板子与电脑是否还在同一网段（见第 3 条）。

`PENDING` 超过 `ttl_s`（默认 120 秒）会转成 **`EXPIRED`**，这是**正常行为，不是故障**：
它准确表达了"指令发出去了，但没人接"。不要把它当成设备坏了。

### 10. 指令停在 EXECUTING / 状态变成 TIMEOUT

这与 `EXPIRED` 含义完全不同：说明**设备已经接手了指令，但没能干完**。
排查方向是设备侧：摄像头初始化是否成功（`CAMERA_ENABLE` 与 PSRAM 配置）、
抓帧是否失败、上传是否超时（`CMD_TIMEOUT_MS`）。串口日志会有对应的 `摄像头抓帧失败` 或 `上传失败`。

> 记住这两条的区别：**`EXPIRED` 找人（设备在不在），`TIMEOUT` 找活（设备干没干成）。**

### 11. 图传上来了，但状态不是 COMPLETED，或 `evidence_ok=false`

看服务端打印的失败理由，它直接点名是哪条证据不过：

| 理由含 | 含义 | 常见原因 |
|---|---|---|
| `E1 不通过` | 观测记录没带本次 `request_id` | 固件未传 `X-Request-Id` 头；或传的是上一次的 |
| `E2 不通过` | `capture_ts` 早于指令下发时刻 | 板端时间未同步（SNTP 失败）导致时间戳倒退 |
| `E3 不通过` | 同一 `boot_id` 内 `seq` 未递增 | 同一张图重传；或 `seq` 被重置 |

E2 的坑最隐蔽：板子没对时成功时，`capture_ts` 可能写成 `uptime+...` 形式，
服务器对这类前缀会**跳过时序比较**（无法比较就不硬判），但仍要求 `request_id` 与 `seq` 正确。
若想演示 E2 拦截，用第 6 章第 3 步的手工构造方式最直观。

### 12. 服务端起不来，提示端口被占用

`server.py` 支持用环境变量换端口和数据目录，方便开一个与主服务端互不干扰的隔离实例：

```bash
set PORT=8100 && set DATA_DIR=./tmpdata && python server.py
```

`selftest_command.py` 配合它使用即可 —— 把地址当参数传进去（`python selftest_command.py http://127.0.0.1:8100`），
这样自测产生的指令行都落在 `tmpdata/` 里，**不会污染你的 `data.db`**。

## 八、本次做的个人修改（提交作业时可写进说明）

1. **传感器选型修正**：任务卡示例是 MPU6050，但 ESP32-S3-EYE **板载 QMA7981**，因此没有外接 MPU6050，改为直接驱动板载传感器，省去接线和供电问题。
2. **驱动依据原厂手册而非二手资料**：网上关于 QMA7981 量程灵敏度的中文博客数值有误（把 ±2g 写成 1024 LSB/g）。本固件按 QST 原厂数据手册 Rev.A 第 20 页 RANGE 表实现，并**显式写入量程寄存器**而不依赖芯片复位默认值，避免换算系数与实际量程不符。
3. **芯片 ID 自检改为软告警**：手册第 19 页写明 0x00 默认值为 "ANA"（由芯片 NVM 决定），并非固定常数；0xE7 只是某台板子的实测值。因此 ID 不符时只打印告警不中止运行，避免因批次差异导致板子罢工。
4. **不产生假数据的三条防线**：传感器初始化失败 → 不上传只报错；单次读取失败 → 跳过本次不编造数值；Wi-Fi 未就绪 → 只重连不重启不缓存。
5. **时间戳诚实降级**：ESP32 无掉电保持 RTC，固件用 SNTP 对时（东八区）。若对时失败，`ts_device` 写成 `uptime+12.345s(time_not_synced)` 明确标注未同步，而不是编一个看似正常的日期。
6. **网页"未更新"判定**：10 秒无新数据即判定停止采集，保留旧值并给出黄色提示与秒数，满足老师"停止采集时页面不能空白也不能跳假数"的检查要求。
7. **控制台配置**：`sdkconfig.defaults` 设 `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y`，适配这块板无独立 USB 转 UART 芯片的设计，否则串口监视器看不到日志。
8. **修复驱动符号扩展 bug（关键）**：QMA7981 输出为 14 位二进制补码，其中 8192~16383 表示负数。原换算未做符号扩展，负值被当成大正数：实测板子平放时读出 `ax=+15.4g / ay=+15.8g`、合成 22.1 g，且原始量 15792 已超出 ±8g 量程上限 8191（物理上不可能）。补上符号扩展后恢复为 `ax=-0.586 / ay=-0.155 / az=+0.694`。
9. **传感器现场标定**：板子静止时只受重力，三轴合成加速度恒为 1.000 g 且与摆放姿态无关，据此可无标准器具标定。实测本片 QMA7981 灵敏度仅约手册标称值的 91%，遂引入 `QMA7981_CALIB_SCALE` 标定系数，标定后合成值 0.9953 g（偏差 0.47%，标准差 0.0035）。重新标定方法写在 `app_config.h` 的注释里。
10. **服务端补齐原始值存储**：原 `readings` 表缺 `ax_raw/ay_raw/az_raw`、`is_new_sample`、`time_synced` 列，INSERT 亦将其丢弃，与"三处对账"要求不符。已补齐建表字段与 INSERT，并用 `ALTER TABLE` 兼容已有旧库。
11. **网页补充原始 ADC 显示**：三张数值卡片下增加 `raw: N`，历史表新增「原始ADC (x/y/z)」列，使网页这一环也能与板端串口直接对账。
12. **新增摄像头实时传图（可选增强）**：驱动板载 OV2640，每 2 秒抓一帧 JPEG 经 Wi-Fi POST 到服务器并落盘，网页同步显示。
    **关键坑**：`esp_camera_init` 默认会在 **I2C 端口 1** 新建 SCCB 总线，但引脚仍指向 GPIO4/5，与 QMA7981（端口 0，同为 GPIO4/5）抢同一对物理线，
    结果是**加速度计也一起读失败、两类数据全部不上传**。修复方式是把 SCCB 引脚设为 `-1` 并指定 `.sccb_i2c_port = I2C_NUM_0`，
    让摄像头**复用**加速度计已建好的总线（I2C 共享总线，0x12 与 0x30 可共存）。
    完整方案、接线与验证记录见 [`摄像头功能方案与Git提交.md`](摄像头功能方案与Git提交.md)。
13. **把"指令"当成一等公民，而不是给 HTTP 接口加个参数**：新增独立的 `commands` 表与 8 态状态机，
    而不是复用 `readings` 表加个 `trigger` 字段。理由是"下发了"和"执行了"是**两件不同的事**，
    只有独立的状态才能表达"设备收到了但没干完"这种中间态。
14. **用三条可机检的证据替代"看起来是新的"**：E1 请求贯穿、E2 时序合理、E3 序号递增。
    三条全部由**服务器自动校验**并落库 `evidence_ok`，不靠人眼看图判断。
15. **坚持 `UPLOADED ≠ COMPLETED`**：帧到达只说明"收到字节"，证据齐全才算完成。
    这个区分是整个第 2 周的核心 —— 如果两者等同，"旧值冒充"永远无法被发现。
16. **超时按"卡在哪一步"分别归因**：`PENDING` 超时记 `EXPIRED`（没人取，找人），
    `RECEIVED`/`EXECUTING` 超时记 `TIMEOUT`（取走了没干完，找活）。
    统一叫"超时"会让排障方向跑偏。
17. **堵死"旧值冒充"的两道闸**：`/api/command/frame` 未完成时**返回 404 而不是回落到最新图**；
    `has_frame` 仅在 `COMPLETED` 时为真，且网页在未完成时**主动清掉 `<img>.src`**。
    这两处都是"刻意不做的功能"，注释里写明了原因，避免后来者"顺手优化"掉。
18. **开机标识用 NVS 计数 + MAC 而非随机数**：`boot_id` 形如 `6ff894-boot7`，
    跨重启唯一且可读；`seq` 在每次真正发送帧时递增，保证同一开机周期内严格单调。
19. **自测脚本设计成可重复运行**：设备号与 `boot_id` 由 `RUN_TAG`（时间 + pid）生成，
    避免第二次运行时读到上一轮的残留 `seq` 而误报失败；连跑两次均 25/25 通过。
20. **每帧都算 SHA-256，元数据永久保留、原图按配额清理**：原图是"存储"，哈希是"证据"。
    清原图不心疼，但哈希一条都不能丢 —— 否则"这一帧当时到底是什么内容"就永远无法回答。
    已清理的帧在画廊里依然在列，取图接口返回 **404 + `sha256`** 而不是含糊的 500。
21. **解析 JPEG 头拿分辨率，不引入图像库**：`jpeg_size()` 只扫 SOF0~SOF3 / SOF5~SOF7 / SOF9~SOF11
    这几个帧头段，跳过 DHT/DQT/APPn；解析不出就返回 `(0, 0)`，画廊显示"—"，**绝不因为解析失败而拒收这一帧**。
22. **清理失败要区分"真失败"和"环境噪声"**：`os.remove` 抛异常后**再查一次文件是否存在** ——
    有些环境（回收站不可用）是先删掉再抛错，此时文件已经没了，不该拖住 `purged_at` 的标记，
    否则会陷入"每轮重试、永远清不掉"的死循环。
23. **`_send_json` 少写一行 `wfile.write(body)`，整套接口全部返回空体**：客户端报
    `IncompleteRead(0 bytes read, N more expected)`，而服务端日志显示 200、毫无异常。
    教训是**响应头里的 `Content-Length` 与实际写出的字节数必须一起看** ——
    这个 bug 靠看日志永远发现不了，只能靠端到端自测。也正因如此，
    本项目的两个自测脚本都跑**真实 HTTP 往返**，不做函数级 mock。
24. **自测脚本显式绕开 HTTP 代理**：本机开着 Clash（`http_proxy` 环境变量），
    连 `127.0.0.1` 的请求都会被劫到代理上，返回 `502 upstream connect failed`。
    两个自测脚本都改用 `build_opener(ProxyHandler({}))`，否则换台机器跑就全红。

> **经验教训：换算自洽 ≠ 数据正确。**
> 符号扩展出错时，`raw ÷ 1024` 与上报的 g 值依然精确吻合，三轴"看起来"完全正常；
> 但合成加速度是 22 g、原始量已超量程——物理量本身根本不可能成立。
> 因此校验 IMU 一定要看**合成加速度 |a| = √(ax²+ay²+az²) 是否 ≈ 1 g**，
> 这是能一票否决大多数驱动 bug 的指标。
