## 二、两个角色：设备使用者 ≠ 数据查看者

课程要"认识"这两个角色，因为**后面三周的设计全是围绕这个区分展开的**。

| | 设备使用者（现场的人） | 数据查看者（远程的人） |
|---|---|---|
| 位置 | 和板子在一起 | 只面对网页 |
| 能看见什么 | 板子本身：LED 在闪、板子被倾斜了、按键按下去的手感 | 只有经过网络搬运过的数字和图像 |
| 能直接做什么 | 按键、移动板子、拔电源 | **什么也做不了**，只能"请求" |
| 他知道的事 | "我按了" | "我看到了" |
| 他的信息特点 | 局部、当下、**不经过网络** | 全局、有延迟、**完全依赖网络** |

### 2.1 这个区分带来的三条设计约束

**① 权限不同：查看者不能直接操作硬件，只能"请求"。**
第 2 周的「远程采集指令」就是这么来的 —— 查看者点一下按钮，板子去拍一张。
而"点一下"和"拍到了"之间隔着整条链路，所以必须有一个 `request_id` 把它们连起来。

**② 可见性不同：查看者看不见板子的本地反馈。**
板子的 LED 亮了，网页前的人**不知道**。
第 3 周的「三层状态」（本地确认 / VPS 接收 / 查看者回应）就是为这个差异设计的 ——
如果压成一个状态，就会出现"板子亮了 = 对方知道了"这种偷换。

**③ 证据来源不同：两句话不是一回事。**
- 现场的人说"我按了" —— 这是**他自己的**观察
- 远程的人说"我看到了" —— 这是**系统告诉他**的

第 2 周防的"旧值冒充"和第 3 周防的"服务端收到就算完成"，病根都是同一条：
**拿一个来源的事实去冒充另一个来源的事实。**

### 2.2 本项目里的两个角色

- **设备使用者** = 持有/佩戴板子的人。第 3 周的"求助者"就是他 —— 他按一下键，是要**别人**知道。
- **数据查看者** = 打开网页的人。第 3 周的"回应者"就是他。

第 1 周只有"使用者产生数据、查看者看数据"这个最简形态；
第 3 周才出现**反向**的信息流（板子主动发起 → 人回应）。

## 三、三方分工与数据流

```
┌─────────────┐   HTTP POST /api/ingest    ┌──────────────┐   HTTP GET /api/latest   ┌────────────┐
│   板端       │ ─────────────────────────► │   服务端      │ ◄─────────────────────── │  浏览器     │
│ ESP32-S3-EYE │                            │ Python+SQLite│                          │  index.html │
│              │ ◄───────────────────────── │              │                          │            │
│ 采集+上行     │   HTTP GET /api/command/poll│ 接收/存储/查询 │                          │ 展示/操作   │
└─────────────┘                            └──────────────┘                          └────────────┘
```

| 环 | 职责 | 它挂了会怎样 | **怎么单独证明它是好的** |
|---|---|---|---|
| **板端** | 采集、打时间戳、上行 | 网页停止更新 | 看串口：有没有"已上报"日志 |
| **服务端** | 接收、存储、查询 | 网页打不开 / 写入失败 | `curl /api/health` + 直接查 `data.db` |
| **浏览器** | 展示与操作 | 数据在库里但页面上看不到 | F12 看 Network，或直接 `curl /api/latest` |

**三者是进程隔离的。** 这张表最右边一列才是重点 ——
排错时不是"猜哪一环坏了"，而是**用一条命令把某一环摘出去**。

### 3.1 一个具体的例子

现象：网页上三轴数值和串口打印的对不上。

- ❌ 直接去读 `main.c` 找 bug —— 方向就错了，因为还没证明不是服务端的问题。
- ✅ 先用 `curl http://127.0.0.1:8000/api/latest` 看服务端返回什么。
  它和串口一致 → **服务端没问题**，问题在浏览器那一段（缓存？渲染？取错设备？）。
  它和串口不一致 → 问题在服务端或链路，板端已经发出去了。

这就是"从链路两端往中间夹逼"。本项目为此专门写了个脚本：

```bash
python 三处对账核对.py              # 板端串口 / 服务端库 / 查询接口 三处并排
python 三处对账核对.py s3eye-group01
```

## 四、单位与时间：怎么核对

### 4.1 单位

原始读数 → 物理量，中间隔着一个换算系数：

| 环节 | 值 | 在哪 |
|---|---|---|
| 芯片量程 | ±8 g（`RANGE=0100`） | `QMA7981_RANGE_BITS` |
| 灵敏度 | **1024 LSB/g**（手册标称） | `QMA7981_LSB_PER_G` |
| 现场标定系数 | 每块板不同，本块实测 `0.8078` | `QMA7981_CALIB_SCALE` |
| 落库单位 | `"g"` | `readings.unit`，网页显示在每个数值后面 |

**怎么核对（唯一不需要标准器具的办法）**：
把板子**水平静止**放好，三轴合成加速度 `|a| = √(ax²+ay²+az²)` 理论上恒为 `1.000 g`，
**与摆放姿态无关**（静止时只受重力）。所以：

> 平放 → 重力所在的那一根轴应该 ≈ 1.000 g。

本项目实测到的三次值（记在 `app_config.example.h` 的注释里）：
`0.9116 → 0.8447 → 0.8078`。三次不同说明这块传感器除灵敏度误差外还有**零点偏移**，
所以单一比例系数没法在所有姿态下都得到 1.000。当前系数按最近一次静止姿态整定。

> **为什么单位写错比数据错更隐蔽**：
> 显示 `0.98` 看着像"接近 1g"，但如果单位其实是 m/s²，正确值该是 `9.8` ——
> **差了 10 倍，却不容易一眼看出来**。所以单位必须随数值一起落库、一起显示，不能靠约定。

### 4.2 时间三要素

| 字段 | 谁的钟 | 用途 |
|---|---|---|
| `ts_device` | **板子的钟** | 只作参考，**服务端不采信** |
| `ts_server` | 服务端的钟 | **判定一律用它** |
| `time_synced` | 板子自己报的"我对上时了吗" | 决定上面那个 `ts_device` 能不能信 |

**本板的实际情况：SNTP 常年失败。** 所以 `ts_device` 经常长这样：

```
uptime+812.500s(time_not_synced)
```

**这不是 bug，是如实标注。** 课程知识点 K1.6 的原话是：
「设备侧时间 / 服务端时间 / 同步状态。**拿不到就诚实标注"未同步"，绝不伪造**」。

> 这一条在第 5 周变成了一个正式设计：时间轴分三档 `device` / `derived` / `server`。
> 详见《状态机与数据契约.md》与《第五周-传感器示波器与姿态孪生.md》。

## 五、无数据 ≠ 请求失败

课程知识点 K1.9：「页面必须区分"没有数据"和"请求失败"，**不能都显示成空白**」。

网页上这四种状态是**分开**的（`server/index.html` 的 `renderLatest` / `setStatus`）：

| 状态 | 触发条件 | 页面文案 | 该去查什么 |
|---|---|---|---|
| **正常** | 最新一条在 15 秒内 | 绿：`实时数据 · N 秒前更新` | —— |
| **数据未更新** | 有数据但最后一条超过 15 秒 | 黄：`数据未更新：最后一条采集于 …（N 秒前），开发板可能已停止上传` | 板子还在吗？串口有输出吗？ |
| **从未收到过数据** | 服务端在线，但库里一条都没有 | 灰：`服务器在线，但还没有任何设备上报数据` | 板子还没配好 / 从没连上过 |
| **请求失败** | 拿不到 `/api/latest` | 红：`无法连接服务器，请确认服务正在运行` | 服务端进程还在吗？ |

**为什么必须分开**：这四句话指向**四个完全不同的排查方向**。
如果都显示成空白或"加载中"，排错时连第一步该干什么都不知道 ——
这和第 2 周"`EXPIRED` 与 `TIMEOUT` 必须分开"是同一个道理。

## 六、★ 部署记录

### 6.1 课程要求 vs 实际情况（如实说明）

课程要求是：**「开发最小接收与存储服务 + 查询接口 + Web 页面，并部署到分配的 VPS 空间」**，
验收标准写的是「**公网可访问**」。

**实际情况：没有拿到分配的 VPS 空间，服务端跑在本机电脑上。**

这不是偷懒，是一个**降级替代**。所以下面把"因此做到了什么"和"因此做不了什么"分开写清楚 ——
免得看的人以为 VPS 那部分也验过了。

| 课程要求的点 | 本机替代后 | 说明 |
|---|---|---|
| 最小接收与存储服务 | ✅ 满足 | 与部署位置无关 |
| 查询接口 | ✅ 满足 | 同上 |
| Web 页面 | ✅ 满足 | 同上 |
| 端口 / 进程 / 日志 | ✅ 满足 | 见 6.2，VPS 上要做的这几件事本机同样做了 |
| 端到端联调（板 → 服务 → 网页） | ✅ 满足 | 见 6.3 |
| **公网可访问** | ❌ **做不了** | 本机在局域网内，没有公网入口 |
| **跨网段访问**（板子在另一个网络） | ❌ **做不了** | 板子必须和电脑连同一个 Wi-Fi |
| **VPS 上的进程守护 / 开机自启** | ❌ **未做** | 本机是手动起、手动关 |
| **真实公网带宽与延迟下的表现** | ⚠️ **反而不如实** | 见下 |

> **⚠️ 一个容易自欺的地方**：本机到板子是同网段直连，**比 VPS 近得多**。
> 所以"本机测着挺好"不能推出"放到 VPS 上也挺好"。
> 事实上本项目这条链路实测的延迟抖动是 **3ms ~ 770ms**（ping 0% 丢包但延迟剧烈波动），
> 已经很难看了 —— 如果换成公网只会更差。
> 这个现象和它的影响记在 `项目复盘与踩坑记录.md` §4。

### 6.3 端到端验证记录

按 README §三 的步骤走一遍，能观察到：

1. `python server.py` 打印两行地址（本机 / 局域网）；
2. 板子上电，串口出现"Wi-Fi 已连接"与周期性"已上报"；
3. `curl http://127.0.0.1:8000/api/health` 返回 `{"ok": true, "server_now": "..."}`；
4. 网页出现三轴数值且每秒跳动；
5. 拔掉板子电源 → 15 秒后网页转黄「数据未更新」；
6. 关掉服务端 → 网页转红「无法连接服务器」。

### 6.4 如果拿到 VPS，照这几步搬

写在这里，是为了让"本机替代"这件事**不留下未说明的欠账**：

1. 把 `server/` 整个目录传上去（`server.py` / `index.html` / `nl_agent.py` / 各 `selftest_*.py`）；
2. 服务器上确认 `python3 --version` ≥ 3.11（只用标准库，不用装依赖）；
3. **换端口并放行**：`PORT=8000`，防火墙/安全组放行入站 TCP 8000；
4. **配进程常驻**（本机没做的就是这一步）：写一个 systemd unit，
   `Restart=always`，`WorkingDirectory` 指向 `server/`；
5. **改板端 `SERVER_URL`** 指向 VPS 的公网地址，重新编译烧录；
6. **注意公网暴露面**：本服务**没有任何认证**，接口可被任何人读写。
   上线前至少加一条反向代理的基本认证，或限制来源 IP；
7. 重跑一遍自测（`selftest_command.py` 等）—— 它们都是打 HTTP 的，换个地址就能用。

> 第 6 条不是套话：这个服务端**没有任何鉴权**，设计前提就是"跑在局域网内、只有自己用"。
> 直接搬到公网等于把一个能写数据库的接口开放出去。

## 七、分层排错过程

课程要求「能**说明自己的排错过程**（不是"我试了好多次"，而是"我如何逐层排除"）」。
本项目完整记录在 `项目复盘与踩坑记录.md`，这里给出方法与一个实例。

### 7.1 方法：从链路两端往中间夹逼

```
板端串口  ──────────────────────────────────────────────►  浏览器
   ▲                                                        ▲
   └── 先证明这端没问题                      先证明这端没问题 ──┘
```

1. **先证明服务端没问题**：`curl` 打接口。它返回对了，服务端就摘出去了。
2. **再证明板端发出去了**：看串口日志。
3. **两端都"没问题"却还是不对** → 问题在**中间**（网络、防火墙、代理）。

### 7.2 一个真实实例：三处数值不一致

- **现象**：网页上三轴数值和串口打印的对不上。
- **第一反应（错的）**：去读 `main.c` 找换算 bug。
- **实际做法**：先 `curl /api/latest`。接口返回的和**串口一致** → 服务端没问题，
  问题在浏览器那一段。最后定位到是页面取错了设备（多设备下拉框的默认值）。
- **为什么"第一反应"是错的**：还没证明不是服务端的问题就改板端代码，
  等于在一个可能没坏的地方瞎改 —— 这正是本项目反复出现的一类错误
  （见 `AI协作记录与提示词归档.md` 案例 4「把网络问题误判成代码问题」）。

### 7.3 一条踩出来的经验

**「服务端日志说成功、板子串口说失败」这种情况，先对比两边的时间戳与条数，别先怀疑代码。**

本项目的链路质量很差（延迟 3ms~770ms 剧烈抖动），
会出现"服务端确实收到了 201，但板子在超时时间内没等到响应"这种**两边都如实**的情况。
它看起来像代码 bug，其实是环境限制。

## 八、已知限制

1. **未部署到 VPS**（第六节）—— 公网可达性、跨网段、进程守护都没验。
2. **服务端无任何鉴权** —— 设计前提是"局域网内自己用"。
3. **`QMA7981_CALIB_SCALE` 是单姿态整定** —— 只能保证"平放时 ≈ 1.000 g"，
   彻底消除零点偏移需要六面法校准，本课程不必做，但要知道它是个近似。
4. **`ts_device` 多数时候不可信** —— 本板 SNTP 常年失败，这是环境限制不是代码问题。
   所以判定一律用 `ts_server`。
5. **时间戳精度**：`ts_server` 用的是服务端本地时钟（毫秒级），没有做 NTP 校正。
